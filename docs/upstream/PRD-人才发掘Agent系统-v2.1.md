## 1. 背景与目标

### 1.1 背景

企业招聘初筛成本高：HR 需在大量简历中完成"理解岗位→比对简历→能力定级→解释理由"的全链路工作，现有工具多停留在关键词过滤与黑盒打分，无法处理非结构化信息（项目描述、作品集），结论不可解释、不可审计。与此同时 LLM Agent 技术已能承载"任务委托式"工作流，但招聘场景中的 Agent 应用多停留在概念层，缺乏**可验证、有合规边界**的完整实现。

**定位（v2.1）：双边偏好的智能匹配平台。**

> 双边**各自导入**自己的材料（企业导入岗位与氛围描述、候选人导入简历与期望），两边**各填一份偏好表单**；
> 系统用**同一套偏好维度与能力量规**给出**可追溯的匹配建议**；**建议不强制，判断权归双方**；
> 每一条结论都可展开到**双方填报与简历原文**。

这一定位经三次调整后收敛（决策全过程见 docs/recruit/13 §1）：①"双向撮合平台"曾被**否决**；②"双端同尺的决策支持层"被**采纳**；③ v2.1 **采纳"双边偏好匹配平台"**。**采纳的前提是本项目补上了一处真实缺口——此前系统对简历侧设六重审查，对标准侧却不设任何审查（JD 一解析即成真理）**，故本版引入 RQ 需求层予以对称（见 §1.2 P6、§6.1）。三条护栏使该定位成立且不退化：**不做撮合结论只做匹配建议 / 匹配依据必须来自双方主动填报字段 / 匹配不得使用百分比与精确分数**。

**必须保留的一句话**：无论称谓如何，"**两侧用同一把尺**"仍是定位成立的必要条件——若哪天两侧各有各的标准，这个定位立刻失效。

### 1.1.1 核心功能与支撑功能（v2.2 新增，**本 PRD 的结构主轴**）

> **一句话**：本系统的**核心功能只有一个——双边偏好匹配（PM 层）**；其余全部模块都是**为它提供输入、保证其可信、或把它的结论投影到某一侧**的支撑件。**这不是"功能清单里的第一项"，而是决定所有其他模块存在理由的那一项。**

**功能依赖图**（箭头方向 = 为谁提供输入）：

```
                        ┌──────────────────────────┐
                        │   ★ 核心功能             │
                        │   双边偏好匹配（PM 层）   │
                        │   双端填报 → 确定性比对   │
                        │   → 四态档位（高/中/低/   │
                        │      无法判断）           │
                        └────────────┬─────────────┘
                                     │ 需要什么输入
        ┌────────────────────────────┼────────────────────────────┐
        │                            │                            │
        ▼                            ▼                            ▼
┌───────────────┐          ┌───────────────┐          ┌───────────────┐
│  JD 层        │          │  RQ 需求层     │          │  EV 评估层     │
│  JD-001~002   │          │  RQ-001~004    │          │  EV-001~011    │
│  岗位结构化    │          │  企业"真要什么" │          │  候选人"有什么" │
└───────────────┘          └───────────────┘          └───────┬───────┘
                                                              │
                        ┌─────────────────────────────────────┤
                        ▼                                     ▼
                ┌───────────────┐                    ┌───────────────┐
                │  MT 初筛层     │                    │  TM 求职者端   │
                │  MT-001~003   │                    │  TM-001~005    │
                │  从简历库选出   │                    │  核心功能的      │
                │  候选集        │                    │  求职者侧视图    │
                └───────────────┘                    └───────────────┘

        ┌─────────────────────────────────────────────────────────┐
        │  SC 标准自检层（SC-001~002）：保证两侧用的是"同一把尺"     │
        │  —— 它不是为匹配提供输入，而是**保证匹配这件事还成立**      │
        └─────────────────────────────────────────────────────────┘
```

**支撑功能分工表**：

| 支撑模块 | 为核心功能提供什么 | 若缺失，匹配会变成什么 |
|---------|------------------|---------------------|
| **JD 层**（JD-001~002） | 岗位的**结构化画像**（硬性/加分/隐性要求，可人工确认） | 匹配的"企业侧"没有依据——只能靠自由文本猜 |
| **RQ 需求层**（RQ-001~004） | 企业**真正要什么**（用人需求画像）+ 要求本身是否站得住（诊断） | 匹配的是**对外广告**而非**对内规格**；且可能匹配一个自相矛盾的标准 |
| **MT 初筛层**（MT-001~003） | 从简历库中筛出**值得进入匹配的候选集** | 匹配无对象；或对全库无效匹配，成本失控 |
| **EV 评估层**（EV-001~011） | 候选人的**能力画像**（档位 + 技能熟练度 + 证据） | 匹配退化成"关键词对关键词"，无法处理非结构化信息，且不可追溯 |
| **TM 求职者端**（TM-001~005） | 核心功能的**求职者侧对等视图**（同一把尺的另一半） | 只有企业侧在匹配——退化回"单端筛选系统"，"双侧"不成立 |
| **SC 标准自检层**（SC-001~002） | 保证两侧的**尺子一致且有效**（可辨识性 + 同级基准） | 匹配在"标准本身有毛病"的情况下照常输出，结论看似严谨实则失真 |

**三条由该结构直接推出的设计纪律**：

1. **支撑件的验收标准，是"它喂给核心功能的东西够不够好"，而不是"它自己看起来多完整"**——例如 EV 层的价值不由"报告做得多漂亮"衡量，而由"它产出的能力画像能否支撑一次有效的偏好匹配"衡量。
2. **核心功能不可被支撑件遮蔽**：任何支撑模块的对外呈现，都不得让用户误以为"这就是产品"（例如把能力定级报告做成产品主界面，会让产品看起来是个筛选工具）。
3. **排期遵循依赖顺序**：核心功能的**最小可用版本（PM-001 必填 3 项 + PM-002 确定性比对 + PM-003 档位输出）必须与它依赖的最小输入集（JD-002 画像确认、RQ-001 需求澄清、EV-001~006 能力定级）同期交付**——**否则交付的是"没有主功能的支撑件集合"**。这是 v2.2 将 PM 层与 RQ-001 前移进 M1 的直接理由（见 §12）。

### 1.2 要解决的问题

| # | 问题 | 本期解决方式 |
|---|------|-------------|
| P1 | 简历初筛耗时、标准不一 | Matching Agent 批量初筛 + 统一量规定级 |
| P2 | AI 评估黑盒、HR 不信任 | 证据强制引用 + 逐维定级理由 + 人工闸门 |
| P3 | Agent 幻觉与过度推断 | 量规锚定 + 缺证据不猜测（记"证据不足"，**不降档**）+ 引用纪律 |
| P4 | 评估主观、无法横向比较 | **区间档位定级**（B1~B5，证据跨档输出区间）+ 确定性档位排序键，**不合成任何总分** |
| P5 | AI 评估的合规与偏见风险 | 敏感属性隔离 + Audit Agent 偏见审计 + 全链路留痕 |
| **P6**（v2.1 新增） | **岗位要求本身不被审查**——JD 自相矛盾（"校招要求 3 年经验"）、超出同级基准（初级岗写"精通"致全员落 B1–B2、失去区分度）、不具备可评性（"有责任心"） | **RQ 层**：需求规格化（RQ-001）+ 要求溯源（RQ-002）+ JD 诊断（RQ-003，**仅三类可确定问题**）+ 需求—评估覆盖校验（RQ-004）；**只陈述事实 + 定位原文，不评价企业、不给改写文案** |
| **P7**（v2.1 新增） | **求职者只能被动接受 JD**——不知要求是否合理、不知自己缺的是事实还是证据 | **TM 层回归**：目标岗位对照（TM-001，含**岗位要求体检**）+ 证据缺口与**量规差距说明**（TM-003，引用量规原文而非给学习建议） |
| **P8**（v2.1 新增） | **双方的偏好没有结构化表达渠道**，匹配只能靠人猜 | **PM 层**：双边偏好表单（必填收敛至 3 项）→ 确定性规则引擎比对 → **高/中/低/无法判断**四态档位，**每档可展开到双方原文**；**不做撮合结论** |

### 1.3 成功指标与口径

> **v2.2 重构说明**：原十二项指标为一维平铺，未区分"衡量核心功能"与"衡量支撑件"。依 §1.1.1 的"核心—支撑"结构，本版将指标**按服务对象分三级**重排（核心 4 项 / 支撑 11 项 / 作品 3 项）。**指标分级的实质意义**：核心指标不达标即产品核心功能不成立，不允许用支撑指标的完备来掩盖；支撑指标不达标属"输入质量受损"，允许先交付后补强。**指标总数仍到此为止，不再新增维度**（v2.2 新增的 2 项核心指标是**机制性指标**，服务于"确定性匹配"这一架构承诺的验证，不构成新维度）。

**① 核心指标（4 项，衡量"匹配本身站不站得住"）**

| 指标 | 定义 | 目标值 |
|------|------|--------|
| **匹配结果可复现性** | 同一对填报快照重复执行匹配，逐维档位与整体档位**完全一致**的比例 | = 100% |
| **匹配档位依据完整率** | 输出的匹配档位中，`ent_quote`（企业侧原文）与 `cand_quote`（候选人侧原文）**均非空**的比例 | = 100% |
| **匹配档位一致性**（v2.2 新增） | **换人（不同操作者）对同一对填报数据执行匹配，档位一致率**——验证"确定性规则引擎"真的不依赖人的随机性 | = 100%（确定性引擎的必然结果；若不为 100% 即为缺陷） |
| **无法判断率**（v2.2 新增） | 必填 3 项（技术方向/自主性/学习与成长倾向）中输出"无法判断"的维度占比 | **记录基线**（不设达标线——该指标的作用是**校准维度设计**：若长期过高，说明维度太抽象需改选项式，见 docs/recruit/13 §11 风险） |

> 核心指标的**共同特征**：它们衡量的是**机制属性**（可复现、有依据、不掺人为主观），而非"匹配得多准"。理由：撮合质量本身没有 ground truth（见 §3.2 与红线 1），**可验证的只能是"依据可追溯 + 结果可复现"**——这是本项目全部可信度的地基。

**② 支撑指标（11 项，衡量各支撑件对核心功能的输入质量）**

| 服务对象 | 指标 | 定义 | 目标值 |
|---------|------|------|--------|
| RQ 需求层 | **需求溯源覆盖率** | 进入 P0 优先级的岗位要求中，带来源标签的比例 | = 100% |
| RQ 需求层 | JD 诊断准确率 | 人工抽检 20 条诊断条目，判定"确属该问题"的比例 | **仅记录基线**（≥80% 后才考虑对外，见 §13 风险） |
| RQ 需求层 | 需求澄清完成度 | 澄清问题被回答（非跳过）的比例 | **仅记录基线** |
| MT 初筛层 | 初筛一致率 | 分批结论与人工标注集（20 对起步，扩至 50 对）一致的比例 | ≥ 75% |
| MT 初筛层 | **baseline 对比优势** | 关键词 baseline 与 Agent 分批在同一标注集上的**一致率**差值 | Agent ≥ baseline +15pp |
| EV 评估层 | **定级一致性** | 同一简历重复定级 3 次，各维度**档位一致率**（不得跨越 B3/B4 边界） | ≥ 90% |
| EV 评估层 | 证据覆盖率 | 能力定级报告中含 ≥1 条简历原文证据的维度占比 | = 100% |
| EV 评估层 | 熟练度定级抽样准确率 | 抽样 20 个技能项，Agent 定级（L1~L4）与人工标注一致的比例 | ≥ 80% |
| EV 评估层 | 人工改档率 | HR 修改维度档位或整份打回的比例（越低说明 Agent 越准） | 记录基线 |
| TM 求职者端 | **求职者端对照一致性** | 同一简历 + 同一 JD 重复执行 TM-001，档位一致率 | ≥ 90%（与 EV 层同口径） |
| SC 标准自检层 | **画像可辨识率** | 标注集简历**反向恢复岗位类型**与标注一致的比例（匹配不出 → 标准有问题，不是候选人有问题） | ≥ 70% |

> **说明**：本表**逐项列出全部支撑指标，不新增、不删除任何一项**（指标总数纪律见下）。其中"JD 诊断准确率""需求澄清完成度""人工改档率"**只记录基线、不设达标线**（表中已标注）——它们的作用是**描述现状与校准设计**（诊断准确率长期偏低说明规则需收紧、改档率长期走高说明定级口径有偏差），而非"必须达成的目标"。

**③ 作品指标（独立于上述两级，衡量"这个作品能不能打"）**

| 指标 | 定义 | 目标值 |
|------|------|--------|
| 链路可演示性 | **双端填报 → 匹配 → 档位依据 → 人工确认** 全流程可演示 | 是 |
| 交付效率 | 从拿到代码到线上可演示所需时间（docker compose 一键） | ≤ 30 分钟 |
| 单份评估成本 | 单份简历端到端 LLM 调用成本（token 折算） | 【假设】≤ ¥0.5/份，跑 10 份实测后回填 |

> 指标设计说明：**核心指标（4 项）衡量"核心功能成不成立"，支撑指标（11 项）衡量"支撑件喂得够不够好"**，作品指标（3 项）按目标岗位 AI 全栈/FDE 补入——baseline 对比证明技术判断力，交付效率证明工程交付能力（FDE 核心），成本指标证明商业化意识。
>
> **指标通胀纪律（v2.1 起，v2.2 延续）**：指标总数**到此为止，不再继续堆**。JD 诊断准确率、需求澄清完成度、人工改档率、无法判断率**只记录基线、不设达标线**，避免指标通胀稀释核心指标的注意力。
>
> **v2.0 范式说明（定级范式收口）**：系统**不产出任何综合分或总分**。评估单位是**档位 B1~B5**，证据跨两档时输出**档位区间**（如 B3–B4）；维度之间**不做算术合成**，排序使用确定性**档位排序键**（达标维度数 → 维度优先级逐维档位 → 证据充分维度数，见 EV-005）；技能按熟练度证据定级（EV-011，L1~L4）而非布尔命中；报告首屏为能力结构视图（EV-009），并显式输出证据不足区与待验证清单（EV-010）。理由见 docs/recruit/07（范式缺陷四机制）与 docs/recruit/08（设计方案）。**匹配层同理**：匹配档位为四态枚举（高/中/低/无法判断），由确定性规则引擎生成，**不产出百分比或分数**（红线 6/12）。
>
> **v2.3 伦理口径（不新增指标，但改变指标的"呈现纪律"）**：本版明确**档位不是用于筛选的门槛，而是用于说明差距的参照**。因此：①**企业端不出现"档位/评级"字样**，一律以"与岗位要求的差距"表述（红线 14）；②**AI 偏差提示须在企业端与求职者端的首屏及页脚默认可见**；③**系统不设任何阈值语义**（无"合格线/达标线/分数线/淘汰线"）。**这三条是呈现纪律，不占指标名额**——它们约束的是"数字怎么被人看见"，而不是"系统算得准不准"。**设计意图：结论的权重越低，用户越会去读依据；而读依据才是本系统真正想促成的事。**（详见 §6.3 第 7 条）

## 2. 名词与术语

| 名词 | 定义 |
|------|------|
| 岗位画像 | JD 解析产物：硬性要求/加分项/隐性能力的结构化 JSON |
| 初筛分批 | Matching Agent 将简历分为 高匹配/潜力/存疑 三档（排序工具，非淘汰工具） |
| **档位（Tier）** | 定级的唯一单位：**B5 显著超出 / B4 达标 / B3 略欠 / B2 明显不足 / B1 不具备**，另有 `insufficient`（证据不足，**不入档**）。档位是**序数等级，不映射分数** |
| **档位区间** | 证据跨相邻两档时输出的区间（如 B3–B4），用于显式表达测量不确定性；**不得退化为档内取分** |
| 量规（Rubric） | 每维度五档**行为锚点**，Agent 定档的唯一依据（**不含分数、无档内微调**） |
| **维度优先级** | 维度的重要性序数（**P0 核心 / P1 重要 / P2 参考**），决定排序键比较次序与报告强调顺序；**不参与任何算术** |
| **排序键（Sort Key）** | 由确定性代码生成的字典序比较键（达标维度数 → 优先级逐维档位 → 证据充分维度数）；**系统不输出综合分** |
| 证据引用 | 定级/匹配结论必须附简历原文片段，无证据不得输出结论 |
| 人工闸门 | Agent 产出必须经 HR 确认/修改/打回后才生效的机制 |
| 校准记忆 | HR 修正记录回流，用于校准后续匹配与定级偏好的持久化数据 |
| 对照简历对 | 仅修改敏感属性的成对简历，用于偏见审计 |
| **用人需求画像**（Hiring Brief，v2.1 新增） | RQ-001 产物：对**内**规格（区别于 JD 这份"对外广告"）。每条需求含 `{内容, 类型(硬性/加分), 来源标签, 可评性, 优先级}`；`未澄清` 项显式标注、**不代填** |
| **岗位要求溯源**（v2.1 新增） | RQ-002：每条岗位要求标注来源之一——`团队能力缺口 / 业务需要 / 合规或硬性制度 / 模板惯性 / 未澄清`。**无来源标签不得进入 P0 优先级** |
| **JD 诊断**（v2.1 新增） | RQ-003：**仅三类可确定问题**——①内部矛盾 ②超出同级岗位基准 ③不具备可评性。输出**事实陈述 + 定位原文**，**不给"这份 JD 好不好"的总评、不给改写文案** |
| **岗位要求体检**（v2.1 新增） | RQ-003 诊断结果的**求职者视角投影**——同一结论、两个方向，不产生两套口径 |
| **岗位对照排序**（v2.1 新增，TM-004） | 对**用户自选的 N 份 JD**（建议 3–20）用 EV-005 同一排序键排序，输出**每一名的依据**。**不扩展到用户未提供的岗位**；界面**不使用"推荐""匹配度排名"**等暗示外部数据源的措辞 |
| **量规差距说明**（v2.1 新增，TM-003） | 引用量规中 R 档与 L 档的**行为锚点原文**，回答"**该档标准是什么、你缺哪类证据**"。**不推荐课程/资源/学习路径，不生成可粘贴文案** |
| **标准自检**（v2.1 新增，SC-001） | 用标注集简历**反向恢复岗位类型**，检验画像本身是否有区分度。**内部使用，无对外接口与页面** |
| **同级岗位基准**（v2.1 新增，SC-002） | 同类岗位要求区间（如"后端校招：Go L2–L3、1 个可验证项目"），来源分 `A 推导基准 / B 合成样例统计 / C 真实回流`。**两个消费者**：RQ-003 诊断依据 + TM-005 对外披露投影 |
| **偏好维度表**（v2.1 新增） | 双边偏好匹配的**唯一版本化配置**（8 维，必填 3 项：技术方向 / 自主性 / 学习与成长倾向）。走 EV-007 版本纪律；**两侧不得各用一套维度** |
| **匹配档位**（v2.1 新增） | 匹配结果的唯一单位：**高 / 中 / 低 / 无法判断**（四态）。**不得使用百分比与精确分数**；每档**必须可展开到双方原文** |
| **无法判断态**（v2.1 新增） | 匹配的**合法输出**——一方未填报或双方口径不同时使用。**不得为"好看"而强行给档**（诚实性设计） |

## 4. 方案对比与选型

| 方案 | 实现成本 | 可解释性 | 可验证性 | 合规可控 | 结论 |
|------|---------|---------|---------|---------|------|
| A：单次 LLM 调用打分（主流竞品做法） | 极低 | 差（黑盒分） | 差（无基准） | 差（无法审计） | 不选 |
| B：**多 Agent 分层 + 量规/规则引擎 + 人工闸门**（本期方案） | 中 | 强（证据+理由） | 强（标注集+一致性） | 强（隔离+审计） | **推荐** |
| C：微调专用评估模型 | 高（标注量大） | 中 | 强 | 中 | 远期演进，需先积累标注数据 |

选型理由：本项目的差异化支点即"Agent 深度 + 可验证评测 + 合规边界"，方案 B 是唯一同时满足三者的路径；方案 A 与红海产品无差异，方案 C 依赖的数据规模本期不具备。

## 5. 用户角色与使用场景

> **v2.2 按 §1.1.1 层级重排**：角色分两类——**核心功能使用者**（双边填报人：企业侧需求澄清人 + 求职者）与**支撑功能使用者**（HR/面试官/运维者，消费支撑模块产出）。**核心功能不产生任何一方独占的界面**：两侧看到的是同一套偏好维度、同一把能力量规、同一种档位表述。

**（一）核心功能使用者（双边偏好匹配）**

| 角色 | 说明 |
|------|------|
| **企业侧填报人（用人经理／需求澄清人）** | 回答 RQ-001 澄清问题、确认**用人需求画像（Hiring Brief）**、填写**企业侧偏好与氛围描述**（PM-001）；**系统不代写、不润色、不评判其内容**。**这一侧的存在是匹配成立的前提** |
| **求职者** | 导入目标岗位 JD（TM-001）与**自己的简历**，填写**个人偏好表单**（PM-002），查看本人适配档位、岗位要求体检与量规差距说明；**不接触企业侧候选人数据** |

**（二）支撑功能使用者（消费支撑模块产出）**

| 角色 | 说明 |
|------|------|
| HR/招聘负责人 | 导入 JD 与简历、审阅能力定级报告、改档/确认与决策（**对候选人形成建议的唯一决策人**） |
| 面试官（可选） | 消费能力定级报告与**缺口追问清单**（EV-008）辅助面试准备 |
| 系统运维者 | 维护量规/维度优先级模板/标准包、查看审计报告与漂移监控 |
| **系统运维者／作者（内部，SC 层，v2.1 新增）** | 运行 SC-001 画像可辨识性自检、维护 SC-002 同级岗位基准；**SC 层无对外接口、无对外页面** |

### 5.1 核心任务流（双边偏好匹配，M1 主线）

> **v2.2 结构原则**：以下流程是产品的**主线**；企业侧筛选流程与求职者侧对照流程是**它的两条输入管线**，不是并列的第二、第三条主线。

```
① 企业侧导入岗位
   JD 粘贴 → JD-001 解析 → JD-002 确认 → RQ-001 需求澄清 → 生成 Hiring Brief
                                                   ↓
                                         PM-001 填写企业侧偏好与氛围
                                                   ↓
② 求职者侧导入材料
   简历导入 → EV 层能力定级（L1~L4）→ 能力画像
                                                   ↓
                                         PM-002 填写个人偏好
                                                   ↓
③ 匹配（确定性规则引擎，非 LLM 自由判断）
   按「偏好维度表」逐维比对 → PM-003 逐维四态档位（高/中/低/无法判断）
                                                   ↓
④ 输出与判断
   PM-004 每档可展开到双方原文（ent_quote / cand_quote 均非空）
   → **建议非强制，双方自行判断**
```

**这条主线的三处不可让渡**：①每一档 **必须**能展开到双方原文；②档位只用 **高/中/低/无法判断** 四态，**不产出百分比、分数、通过率**；③两侧填报字段 **同源**（偏好维度表为唯一版本化配置）。

### 5.2 支撑任务流（为核心功能服务）

**企业侧筛选（服务于"匹配的一端"）**：HR 粘贴 JD → 确认岗位画像 → 上传/选择简历库 → MT 层初筛分批 → EV 层逐份能力定级 → HR 审阅报告（改档/确认/打回）→ 按**档位排序键**输出候选人名单 → 修正回流校准下一批。

**求职者侧对照（服务于"匹配的另一端"）**：求职者粘贴目标 JD → 填写个人偏好 → 系统输出**对照档位 + 岗位要求体检 + 量规差距说明**；粘贴多份 JD 时输出**岗位对照排序**（每名附依据）。

**两者的产出共同喂给核心功能**：企业侧筛选产出**企业视角下的候选人能力画像**，求职者侧对照产出**求职者视角下的岗位适配视图**；PM 层在此基础上只做一件事——**把两侧的偏好放到同一张维度表上比对**。

### 6.1 JD 与需求层（JD-001~002 + RQ-001~004，v2.1 扩充）

> **本节服务于核心功能的"企业侧输入"**：PM 层匹配的是"企业**要什么**"与"候选人**有什么**"。若企业侧输入直接拿 JD，匹配的就只是**一份对外宣传文本**——JD-001/002 负责把 JD 结构化，**RQ-001 负责把"对外广告"翻译成"对内规格"**。缺 RQ-001，PM 层的企业侧输入即不成立。
>
> **本节 v2.1 的实质变化**：原 §6.1 只有"把 JD 解析成画像"两步——**JD 一解析就变成真理**。v2.1 在解析之后补入 **RQ 需求层**，让"岗位要求"本身也成为被审查对象（对应 §1.2 P6）。设计原则是**把证据纪律延伸到标准侧**：

| 现有纪律（对候选人） | 延伸后（对标准） |
|---------------------|-----------------|
| 每条结论必须附简历原文引用 | 每条岗位要求必须附 **JD 原文 / 澄清记录**，并标注**来源** |
| 无证据不定档 | **无来源标签的要求不得进入 P0 维度优先级** |
| 缺证据标 `insufficient`，不猜测 | 需求未澄清标 `未澄清`，**不替填写人猜** |
| 结论表述纪律：不做能力断言 | 诊断表述纪律：**只陈述事实 + 定位原文，不做 JD 好坏评价** |
| 配置版本化 + 冻结（EV-007） | 需求画像同样版本化（沿用 EV-007 纪律，**不新增编号**） |

**JD-001 JD 结构化解析** P0

- 系统应当将 JD 文本解析为岗位画像 JSON：硬性要求（学历/专业/技能门槛）、加分项、隐性能力、岗位职责摘要；每字段附 JD 原文引用。
- 验收：Given 一份 800 字技术岗 JD，When 执行解析，Then 输出 schema 校验通过的岗位画像，硬性要求字段均可定位 JD 原文出处；解析失败（非 JD 文本）返回明确报错并允许人工手工录入画像。

**JD-002 岗位画像人工确认** P0
- 系统应当在解析后进入人工确认页，HR 可修改任意字段；确认后版本化锁定（version 字段），作为后续匹配与**定级**的唯一输入。
- 验收：Given HR 将"硬性要求-学历"由本科改为硕士，When 提交确认，Then 后续**定级**引用 v2 画像且事件留痕。

**RQ-001 需求规格化（Structured Hiring Brief）** P0（v2.1 新增；**v2.2 前移 M1**——它是 PM 层企业侧输入的唯一来源）

- 系统应当在 JD 解析完成后，生成 **5-7 个结构化澄清问题**（不是开放式问卷），覆盖四类：①**目的**（这个岗位解决什么问题？6 个月后什么样算成功？）②**不可妥协项**（哪 1-2 条是硬门槛？）③**可培养项**（哪些要求可入职后补？）④**来源**（哪些来自团队现状缺口、哪些来自业务需要、哪些是沿用模板？）。
- 产出**用人需求画像（Hiring Brief）**：每条需求含 `{内容, 类型(硬性/加分), 来源标签, 可评性, 优先级}`。
- **硬约束**：①问题数 ≤7；②每题给定选项，避免空白答题；③允许"不清楚/跳过"，记为 `未澄清`，**不得代填**；④`未澄清` 项在报告中显式显示为"需求未澄清"，**不参与 P0 优先级**。
- **区分 JD 与 Brief 是有意设计**：JD 是"对外广告"，Brief 是"对内规格"。**JD 文本缺失但需求真实存在** → 补进 Brief 并标注来源为"澄清补充"。
- **填写负担纪律**：澄清问题**不得成为新表单**——每题给选项、允许多数题跳过；用户明确诉求是"填的东西太多是雷点"。
- 验收：Given 一份含模板套话的技术岗 JD，When 执行规格化，Then 生成 ≤7 个澄清问题且每题有选项；Given 填写人对某题选择"不清楚"，Then 该需求标 `未澄清` 且不进入 P0 优先级，报告显式提示而不猜测内容。

**RQ-002 岗位要求溯源（Requirement Provenance）** P1（v2.1 新增，阶段 2）

- 每条岗位要求须标注来源之一：`团队能力缺口` / `业务需要` / `合规或硬性制度` / `模板惯性` / `未澄清`。
- **硬纪律**：**无来源标签的要求不得进入 P0 维度优先级**（可保留在画像中，但不作为核心门槛）。
- 诊断联动：标签为 `模板惯性` 的要求，进入 RQ-003 的诊断重点。
- 验收：Given 某岗位 6 条要求，When 完成溯源，Then 每条均带来源标签；Given 一条要求未标注来源，Then 该条无法被设为 P0 优先级且界面给出说明。

**RQ-003 JD 诊断（JD Diagnosis）** P0（v2.1 新增，阶段 2）

只做**三类可确定、可定位原文**的诊断，不做主观评价：

| 类型 | 判定方式 | 输出示例（陈述句） |
|------|---------|-------------------|
| ① **内部矛盾** | 结构化字段比对（学历/经验年限/技能等级/届别互斥） | "该 JD 同时出现『校招/应届』与『3 年以上工作经验』，二者互斥（原文：…）" |
| ② **超出同级岗位基准** | 对照 **SC-002 同级岗位基准**（聚合区间） | "该岗位 D4 技能要求为 L4，同级岗位基准为 L2–L3，高出 1–2 级" |
| ③ **不具备可评性** | 判定该要求能否从简历/作品获得证据 | "『有责任心』无法从简历或作品获得证据，建议移入面试考察（原文：…）" |

- **输出形态**：诊断清单，每条含 `{类型, 定位原文, 事实陈述, 涉及维度}`；**不给"这份 JD 好不好"的总评**（与 EV 层表述纪律一致）。
- **边界**：**不评价企业、不评价薪酬、不提供改写后的 JD 文案**（改写属"代写/包装"类，见 §6.9 红线 4）。
- **双端投影**：同一份诊断，企业侧显示为"待确认项"（供 HR 修正需求），求职者侧作为 **TM-001 的"岗位要求体检"** 组成——**同一结论、两个方向，不产生两套口径**。
- 验收：Given 一份"校招岗要求 3 年经验"的 JD，When 诊断，Then 输出内部矛盾条目并定位两处原文；Given 一条"精通分布式"、同级基准为 L2–L3，Then 输出超基准条目含基准来源标注；Given 一份无上述问题的 JD，Then 返回"未发现可确定的问题"（**不硬造问题**）。

**RQ-004 需求—评估覆盖校验（Alignment Check）** P1（v2.1 新增，阶段 2）

- 定级报告生成时校验：所有 `不可妥协项` 与 P0 优先级需求，**必须有对应的评估维度 + 量规可评条目 + 证据要求**。
- 若某 P0 需求无量规覆盖 → 告警"该需求当前不可评估"，进入待处理清单；**不允许 Agent 自由发挥去评**。
- 这是**需求层与评估层的唯一强耦合点**，也是防止"标准悬空"的闸门。
- 验收：Given 一条不可妥协项未映射到任何评估维度，When 定级完成，Then 报告标注"该需求不可评估"并留痕，且不生成该需求的任何档位结论。

### 6.2 Matching Agent 初筛层（MT-001~003）

> **本节服务于核心功能的"候选集供给"**：PM 层需要一份**可评估的候选集**。若候选集规模或质量失控，匹配的输入侧就没有落点。MT 层只做"收敛到可评估范围"，**不产出任何匹配结论**——匹配结论属 PM 层。
**MT-001 简历批量解析与结构化** P0
- 系统应当支持批量导入简历（PDF/文本，合成数据管道），解析为统一候选人档案：基本信息、教育、成绩（GPA/排名）、项目经历、技能清单、实习经历；联系方式字段隔离存储（对评估 Agent 不可见，见 §10）。
- 验收：Given 50 份合成简历批量导入，When 解析完成，Then 每份档案 schema 校验通过，解析失败个体进入人工队列不阻塞批次。

**MT-002 逐条比对与三档分批** P0
- 系统应当对每份简历逐条比对岗位画像硬性要求与加分项，输出：命中清单、缺口清单（各附简历原文证据）、匹配分档（高匹配/潜力/存疑）及分档理由。
- 验收：Given 岗位画像要求"熟悉 Python"且简历写"了解 Python"，When 执行比对，Then 缺口清单命中该条并引用原文"了解"，不得表述为"满足"。

**MT-003 硬性门槛规则过滤** P0

- 系统应当以**确定性规则**（非 LLM）执行硬性门槛过滤（如学历不达标），与软性匹配分离；规则命中仅标记"未达门槛"并附规则编号，不删除简历。
- 验收：Given 规则"硬性要求-学历=硕士"与一份本科学历简历，When 执行过滤，Then 该简历标记未达门槛但仍在列表可见（排序末位），理由可追溯到规则配置。

### 6.3 Evaluation Agent 评测层：能力定级系统（EV-001~011，详设见 docs/06/07/08）

> **本节服务于核心功能的"能力尺"**：PM 层要比较两侧偏好，前提是**两侧共用同一把能力量规**。EV 层是这把尺的**生产地与唯一版本源**——企业侧看候选人用它定档，求职者侧看自己用它说明差距（TM-003）。**若两侧各有一套定级口径，"双边同尺"立刻失效，PM 层退化为两个互不相干的单端工具。**
>
> **范式（v2.0）**：本层**不产出分数**。每个维度输出**档位 B1~B5**（证据跨档时输出**档位区间**），维度之间不做算术合成；跨候选人比较使用**确定性档位排序键**（EV-005）。

> **结论表述纪律（EV 层通用，P0，v2.0 新增）**：系统是**证据整理者，不是能力认定者**——报告只陈述"证据是什么、档位是什么"，不代替面试作能力判定。设该纪律的动机：评估结论的证据来源是候选人自述的简历文本，系统**没有能力也不应判断其真实性**；若系统以"确证"口吻输出，或对个体标注"未核验"，既会误导企业，也会给双方带来纠纷面。
> 1. **两段式输出**：每条结论均为"**证据原文引用 + 档位**"，两者之间不得插入系统口吻的能力断言。
> 2. **禁用词**（作为系统结论时）：具备 / 掌握 / 精通 / 确实 / 证实 / 认定。**引用简历原文时按原文照录，但须加"简历自评/简历写明"前缀**（如"简历自评精通"，而非系统直接下"精通"结论），避免系统结论与简历自述混为一谈。
> 3. **统一表述**：简历显示 / 简历描述 / 依据简历原文 / 简历自评。
> 4. **不确定性提示的呈现边界（硬约束）**：涉及"验证、追问、待确认"的提示**仅允许出现在两处**——① 报告的**面试准备区**（EV-008/EV-010，服务面试官备面，属面试官本来就要做的动作）；② 报告**页脚的使用说明**。**首屏结构视图、维度档位表、排序页、看板等位置一律不得**出现"未核验/待核验/真实性"类标签、徽标或颜色标记，**不得在候选人之间对证据的可核验性作差异化呈现**。
> 5. **人才端边界（TM 模块）**：不得要求求职者核验、不得催促补充材料、不得以任何方式提示其简历不可信；面试准备类提示同样只面向企业侧，不向求职者展示。
> 6. **设计意图（面试可讲）**：系统给出分析与证据，但**"是否进一步调查、是否从某处察觉存疑"的判断余地，明确保留给企业与求职者双方**——这不是功能缺失，是刻意留出的空间。
> 7. **档位的两端呈现区分（v2.3 新增，P0 硬约束）**：**同一套档位，两端不说同一种话。**
>    - **企业端不使用"档位"字样**，一律以**与岗位要求的差距**表述（见 §6.3 末段"企业端呈现规范"）。理由：企业端若直接看到"B2 档"，极易将其当作**筛选分数线**使用（"B2 以下不看"），使系统从"辅助判断"滑向"替代判断"——**这与本系统"辅助而非引导"的定位直接冲突**。
>    - **求职者端保留档位**，用于回答"我离这个岗位的要求差多远"（TM 层）。理由：求职者需要的是**可行动的差距认知**，"差 1 级"比"高/中/低"这种模糊语义词更有用；且档位必须**始终与某一个具体岗位要求成对出现**，不得出现脱离岗位的"你的技术等级"。
>    - **两端的底层判定完全同源**（同一量规、同一 `rubric_version`、同一档位），**差异仅在措辞层面**——这既保住了"两侧用同一把尺"，又避免了同一把尺在两端造成同一种压迫感。
>    - **企业端措辞统一为"与岗位要求的差距"**（高于要求 / 相符 / 低于要求 {n} 级），**且"匹配度"一词同样不在企业端出现**。⚠️ **v2.3.2 修正**：v2.3 原稿曾以"匹配度"作企业端替代词（见变更记录），但落地评审发现该词**天然带数字联想**（易被读成"匹配度 87%"），风险未真正消除；且与本条第 1 款"一律以**与岗位要求的差距**表述"自相矛盾。**故统一收口为"差距"句式，"匹配度"列入企业端禁忌词。**
>    - **实现铁律（防退化）**：两端渲染**必须复用同一份定级/匹配结果记录**（同一 `match_id`、同一 `rubric_version`、同一档位序数），**仅渲染层做措辞映射**；**严禁为企业端单独计算一套"匹配度"**——那样红线 13（两侧口径同源）与本条会同时失效。**措辞映射与偏差提示文案集中于 `config/presentation`（`GET/PUT /config/presentation`）统一管理**，不散落于页面代码，以防文案漂移导致本条失效。

**企业端呈现规范（v2.3 新增，P0）**

> 本节定义企业端**所有档位类信息的对外措辞**。**判定逻辑不变，只改说法**——目的是让档位"可辅助、不可当线"。

| 位置 | ❌ 禁止写法 | ✅ 规定写法 |
|------|-----------|-----------|
| 候选人列表/排序页 | "D3：B2 档"、"B2 以下"、"未达 B3" | "**D3 项目经验：与岗位要求相比，证据支持水平低 1 级**" |
| 能力定级报告首屏 | 直接展示档位矩阵（B1~B5 裸值） | 展示**相对岗位要求**的证据对照（高于/符合/低于要求，及相差级数） |
| 报告维度明细 | "档位：B4" | "**岗位要求 L3，简历证据支持 L2，相差 1 级**"（或"与要求相符"） |
| 排序与导出 | 按档位序数冒烟展示 | 排序逻辑不变（EV-005 档位排序键），但**界面不显示序数，只显示相对关系** |
| 全局 | "**合格线**""**达标线**""**分数线**""**淘汰线**" | 一律不使用；**系统不设任何阈值语义** |
| 全局 | 百分比、"匹配度 87%" | 一律不使用（红线 6） |
| 全局 | "**匹配度**"（v2.3.2 补入） | **企业端不使用**——统一说"与岗位要求的差距"。理由：该词带数字联想，与本表第 1 行"差距"句式重复且风险更高 |
| 页脚/首屏提示 | — | 必须出现 **AI 偏差提示**（见下） |

**AI 偏差提示（v2.3 新增，P0）**

- **强制出现位置**：能力定级报告**首屏**与**页脚**各一处（区别于第 4 条的"不确定性提示"，本条是**面向结论可靠性的一般性提示**，故允许并**要求**在首屏出现）。**本条所称"结果页"指 UI 文档（docs/recruit/02）中的企业端 P4 报告 / P5 排序 / P11 匹配建议，与求职者端 P8 / P13 / P14**——凡展示档位类结论的页面，均须含本提示。
- **规定文案（可用其一，不得自创更弱表述）**：
  - 首屏："**本结果由 AI 依据简历文本整理，可能存在偏差，仅供辅助参考。**"
  - 页脚："**本报告由 AI 自动生成，可能存在偏差；结论仅供辅助参考，请结合面试与实际沟通综合判断。系统不设合格线，亦不代表任何录用判断。**"
- **硬约束**：① **不得省略**"可能存在偏差"与"不设合格线"两个要素；② 措辞**不得反向强化结论权威**（禁"经 AI 严格评估""精准匹配"）；③ 提示**不得做成需要点击才可见**（须默认可见）。
- **设计意图（面试可讲）**：这是一个**主动降低自身结论权重**的产品决策——多数 AI 产品倾向于夸大结论的确定性，本系统**刻意在首屏就提示"可能不准"**，因为该系统的价值主张是"帮你看到证据"，不是"替你下结论"。**结论权重越低，用户越会去读依据；读依据才是本系统真正想促成的事。**

**EV-001 量规锚定定档** P0
- 系统应当按维度量规（五档行为锚点）执行**定档**：先按锚点判定命中的档位，输出档位标识（B1~B5）；**不设档内取分、不设 ±微调**；量规为版本化管理数据。
- **跨档判定**：当证据同时部分满足相邻两档的锚点特征时，输出**档位区间**（如 B3–B4）并标注"证据跨档"，**不得取中间值伪造精确度**。
- 验收：Given D3 项目经验量规与一份含 2 个对口核心项目+量化成果的简历，When 定级，Then 落 **B5 档**且定级理由引用项目原文；Given 一份"方向对口但角色边缘"的简历（部分满足 B4、部分满足 B3），When 定级，Then 输出 **B3–B4 区间**并标注跨档原因。

**EV-002 评估维度与维度优先级** P0

- 系统应当内置 D1 专业匹配度、D2 学业成绩表现、D3 项目经验对口程度，支持 D4 技能匹配度、D5 实践/实习相关度开关；**维度重要性以优先级序数表达（P0 核心 / P1 重要 / P2 参考），不设百分比权重、不做 Σ=100% 校验**；优先级决定排序键比较次序与报告强调顺序，**不参与任何算术**；专业相关性判断依据"专业-领域映射配置表"而非 LLM 自由判断；院校层次不作为任何维度加分项。
- **模板校验（替代原 Σ=100% 校验）**：至少 1 个 P0 维度；同一维度不得重复配置优先级；启用的维度须全部有优先级。校验失败拒绝保存。
- **v1.3 设计判断（保留）**：技术岗招聘现实中项目与技能是主信号，学业成绩是弱信号且存在公平性争议；故默认模板将 **D3 设为 P0 核心、D2 设为 P2 参考级**（见假设 H2，M0 访谈后可上调）。
- **v1.6 更新（保留）**：D4 技能匹配度的口径由"布尔命中率"改为 **"熟练度达标度"**（见 EV-011）；**D4 维度档位 = 岗位硬性要求技能达标档位的中位数（偶数项取靠低者，保守取向）**；加分技能档位仅作并列展示，不参与 D4 档位判定。
- 验收：Given 关闭 D4/D5 的模板，When 保存，Then 报告仅展示启用维度且排序键按启用维度生成；Given 模板缺少 P0 维度或同一维度配置了两个优先级，When 保存，Then 拒绝并提示具体错误；Given 使用默认技术岗模板，When 查看报告，Then D2 显示为 P2 参考级且维度列表按优先级排序。

**EV-003 成绩标准化与 D2 定档** P0
- D2 维度应当将 GPA 按分制换算为百分位（GPA÷满分×100），排名优先于 GPA（百分位=(1-排名/总人数)×100），**按百分位落档**（档位锚点见 docs/07 §A.2）；奖学金作为**档位上调**参考（最多上调 1 档）。
- 验收：Given 简历写"GPA 3.5/4.0"，When D2 定级，Then 按 87.5 百分位落 **B4 档**并展示换算过程；Given 写"GPA 3.5"无满分且侧写有国家级奖学金，When 定级，Then 按 4.0/5.0 双算取**保守档位**后上调 1 档，并标注"换算待确认"。

**EV-004 缺证据处理** P0
- 系统应当对证据不足的维度标记 `insufficient`、**不入任何档位、不虚构分数、不按最低档计**；该维度**不参与排序键比较**（排序时跳过并记录"因证据不足未参与比较"），并在报告的**证据不足区**显式列出（EV-009）。
- **取消原 redistribute / zero 两种权重模式**——二者均为分数合成体系的产物，定级范式下不存在"权重重分配"问题。
- 验收：Given 一份无 GPA 的简历，When 定级，Then D2 标记 `insufficient`（显示"证据不足"而非"低档位"）、其余维度正常定档、报告在证据不足区列出 D2，且排序依据说明中标注"D2 未参与比较"。

**EV-005 档位汇总与排序键生成** P0（v2.0 替代原"综合分计算"）
- 系统应当由**确定性代码**生成候选人的**档位排序键**（**不生成任何综合分或总分**），字典序三键：
  1. **达标维度数**（档位 ≥B4 的维度数，降序）——先看有没有短板，再看有多少亮点；
  2. **按维度优先级逐维比较档位序数**（降序）：先比 P0 维度，再比 P1，同级内按维度序号；
  3. **证据充分维度数**（降序）——档位相同时，证据更充分者优先。
- 排序结果**必须并列展示各维档位**（含区间与证据不足标记）；界面**不得出现任何形如"82.4 分"的合成数值**；LLM 不参与排序键的任何组成部分。
- 低置信（≥2 维证据不足或存在无证据推断）报告整体标注"建议人工复核"。
- 验收：Given 两份候选人能力定级报告，When 排序，Then 排序结果可由上述三键完全复现且界面无任何总分；Given 同一简历重复定级 3 次，Then 各维档位一致率 ≥90%（脚本断言）且不跨越 B3/B4 边界。

**EV-006 能力定级报告** P0
- 系统应当输出报告：**首屏能力结构视图（EV-009）** → 技能熟练度矩阵（EV-011）→ 维度档位明细（档位/区间/定级理由/可展开证据/维度优先级）→ 面试准备区（待验证清单 EV-010 + 缺口追问清单 EV-008）→ **排序依据说明区**（说明本人在批次中的比较依据：达标维度数、首要比较维度、因证据不足未参与比较的维度）；含置信度、定级元信息（Agent/模型版本/时间/量规版本/标准包版本）、人工操作区（确认/单维改档需填理由/整份打回重评）。
- **报告内不出现任何总分、分数或百分比权重**（v2.0 硬约束）。
- **报告页脚固定一句使用说明**（轻口径，不做视觉强调、不进首屏）：「本报告依据简历文本整理，结论供招聘决策参考，请结合面试与实际沟通综合判断。」措辞**不得出现"未经核验""真实性"等字眼**（见 §6.3 结论表述纪律）。
- 验收：Given 一份完整能力定级报告，When HR 将 D3 由 B4 改为 B3 并填理由，Then 报告更新且留痕（改前/改后/理由/操作者/时间）并写入校准记忆；Given 报告已渲染，When 检查首屏、档位表与排序页，Then 无任何总分或分数元素、且**无任何"未核验/待核验"类标签或差异化标记**；Given 查看报告页脚，Then 呈现固定使用说明句。

**EV-011 技能熟练度定级** P0（v1.6 新增）
- 系统应当对岗位画像中的每项技能（硬性要求与加分项）执行 **L1~L4 证据锚定定级**：L1 了解（仅出现技能名）/ L2 熟悉（有使用场景描述）/ L3 熟练（有可验证产出：功能上线、指标改善、作品链接）/ L4 精通（深度证据：架构设计、性能优化并量化、开源贡献、技术分享、专利论文）；L0 = 无证据（仅见于自我评价套话）。
- **三条硬纪律**：①**以证据定级、不以自述定级**——自述等级高于证据等级时按证据等级记录，并生成待验证条目（EV-010）；②不得跨级推断（使用过某技能不得推出相邻技能或更高等级）；③每个等级须附 ≥1 条简历原文引用，无引用不得定级。
- **措辞约束**（见 §6.3 结论表述纪律）：熟练度等级表示"**简历证据所支持的水平**"，**不得表述为对个人能力的认定**——报告一律写作"简历证据支持 L2"，不写"候选人具备 L2 水平"；L4 的锚点名"精通"仅作等级标签，引用时必须写"**简历自评精通**"。
- **达标档位**：设岗位要求等级 R、证据等级 L，按**档位**换算——`L ≥ R+1` → **B5 显著超出** / `L = R` → **B4 达标** / `L = R−1` → **B3 略欠（通常可短期弥补）** / `L = R−2` → **B2 明显不足** / `L ≤ R−3` → **B1 不具备**；`L = L0` → `insufficient`（证据不足，**不入档**）。**档位不含分数、不设档内取分**。
- 验收：Given 简历自评"精通 Redis"但仅有"课程项目中使用 Redis 做缓存"一条描述，When 定级，Then 记为 **L2**（非 L4）且待验证清单生成"简历自评高于描述"条目（措辞为中性事实陈述）；Given 岗位要求 Kafka 精通（R=L4）而候选人证据 L2，When 计算达标档位，Then 该技能落 **B3** 并在短板区标注"差 2 级"。

**EV-009 能力结构视图** P0（v1.6 新增）
- 系统应当在报告首屏输出三区块结构视图，**作为报告主视觉**（报告不再有总分，首屏即结构）：
  - **优势区**：维度或技能簇档位 ≥B4 且证据充分（B4 展示为"达标"，B5 展示为"显著超出"）；
  - **短板区**：档位 ≤B3 **且证据充分**（无证据不进此区，避免把"未知"误判为"差"）；
  - **证据不足区**：档位 = `insufficient` 或技能为 L0。
- 系统应当自动生成一段**结构摘要句**，须包含三要素：优势、短板（含差距级别，如"差 2 级"）、**面试可进一步了解的部分**（中性陈述，如"Kafka 方面简历描述较少"；**不得写"真实性存疑""疑似夸大"类判断**）。
- 验收：Given 一份五维均有充分证据的报告，When 生成结构视图，Then 三区块正确填充且摘要句包含优势/短板/待验证三要素；Given 某维度无任何证据，When 生成报告，Then 该维度进入证据不足区（**不显示任何档位或分数、不进短板区**），且在排序依据中标注"未参与比较"。

**EV-010 待验证清单** P1（v1.6 新增）
- 系统应当为**面试环节**生成"可当面了解"的条目（**呈现位置限报告的面试准备区**，见 §6.3 结论表述纪律第 4 条），两类触发：①**简历自评与描述存在落差**（自评等级高于证据支持等级）；②**关键项缺失**（岗位硬性要求技能为 L0，或核心维度证据不足）。条目一律采用**中性陈述 + 面试可了解角度**（如"Redis：简历自评精通；现有描述为课程项目缓存场景"），**不写"真实性存疑""疑似夸大"等判断性措辞**。
- 与 EV-008 的关系：**EV-010 = 要问什么；EV-008 = 具体怎么问**；两者共用同一份缺口数据，UI 可合并为"面试准备区"（先清单、后追问）。
- 验收：Given 一份含 1 项"简历自评高于描述"与 1 项硬性要求缺失的报告，When 生成清单，Then 两类条目各 ≥1 条且均引用对应证据或缺口位置、措辞为中性事实陈述；Given 无任何缺口，When 生成，Then 返回"无待验证项，建议常规面试"（不硬造）。

**EV-007 定级校准与量规冻结** P1
- 系统应当支持用标注集子集（≥20 对）校准：Agent **档位与人工标注档位的一致率**达标（≥80%，且跨 ≥2 档的严重偏差 ≤10%）后冻结量规 v1；校准结果进入评测报告。
- 验收：Given 20 对校准集，When 运行校准脚本，Then 输出**档位一致率与严重偏差率**及量规版本锁定记录。

**EV-008 缺口追问清单生成** P1（v1.4 新增，由阶段 2 提前的轻量版）
- **功能定位**：面向面试官的**派生能力**，不生成通用面试题库，而是从已确认**能力定级报告**的**缺口维度与证据**出发，为每个缺口生成验证性追问，帮助面试官核实"Agent 判不准的地方"。
- 系统应当对已确认的报告，针对每个**低档位（≤B3）/ 证据不足 / 档位区间跨档**的维度，生成 ≥1 条追问；**每条追问必须引用该维度的缺口证据**（沿用证据强制引用纪律）。
- **边界**：本功能不生成完整结构化面试题库（属阶段 2 完整版）；不输出"该候选人是否合格"的结论；追问清单为面试官参考材料，面试结论由人工作出。
- **错误兜底**：生成调用失败时报告不受影响，追问区显示"生成失败，可重试"，不阻塞报告查看与候选人排序。
- 验收：Given 一份含 2 个缺口维度（D3 落 B3 档、D5 证据不足）的已确认报告，When 生成追问清单，Then 输出 ≥2 条追问、每个缺口维度均有覆盖、每条追问引用报告中的缺口证据；Given 一份五维全 B5 无缺口的报告，When 生成，Then 返回"无显著缺口，建议常规面试"而非硬造问题。

### 6.4 人工闸门与校准记忆（SYS-001~003）

> **本节服务于核心功能的"可信度"**：PM 层的档位必须**可被人工推翻并留下痕迹**——否则"建议非强制"只是句口号。SYS-001 保证未确认结论不进入对外输出；SYS-002 保证人工修正**回流**为下一次判断的依据，使核心功能随使用而校准，而非固定不变。

**SYS-001 报告生效闸门** P0：能力定级报告须经 HR 确认后才标记"已确认"并可进入候选人排序输出；未确认报告不进入比较视图。
**SYS-002 校准记忆** P0：HR 每次改档/打回记录（岗位、维度、**档位变化方向**、理由）写入记忆；下一批**定级** prompt 注入该岗位历史修正模式；记忆写入需确认且可回溯删除。
**SYS-003 不打回风暴熔断** P1：同一岗位连续 3 份报告被整份打回时，系统应暂停**自动定级**并提示检查岗位画像或量规（防系统性错误空转）。

**SYS-004 标准包（Rubric Pack）导入导出** P1（v1.5 新增）
- **定位**：把"量规 + **维度优先级模板** + 专业-领域映射表 + 校准记录"打包为带版本号的配置包（`pack_version`），支持导出为 JSON、导入到任意岗位、复制为新岗位的起始标准——**换客户/换岗位只改配置不改代码**（FDE 交付能力的关键载体）。
- 系统应当：①导出当前生效配置为单个 pack 文件（含 pack_version / rubric_version / **priorities（维度优先级）** / major_map / 校准记录摘要 / 导出时间）；②导入 pack 时校验结构完整性与**优先级配置完整性（至少 1 个 P0 维度、同一维度不得重复配置优先级、启用维度须全部有优先级）**，校验不通过拒绝导入并给出具体错误；③导入后新批次定级生效，**存量报告不回溯**（与 EV-007 一致）。
- **边界**：pack 不含任何候选人数据、审计日志或模型密钥（防数据泄漏）；不提供在线商店/自动分发。
- 验收：Given 从技术岗导出的 pack，When 导入到新建岗位并定级，Then 报告元信息显示该 pack 版本、维度优先级与量规与该 pack 一致；Given 篡改 pack 删除 D3 的优先级配置或使同一维度出现两个优先级，When 导入，Then 拒绝并提示具体缺失项。

**SYS-005 数据来源标记与环境隔离** P1（v1.9 新增）
- **定位**：支持"测试期把合成数据当真实数据用、交付前精确清空"的工作方式，并防止清理残留造成假事实。
- 系统应当：①所有业务记录写入 `data_origin`（synthetic / real）与 `env`（dev / demo / prod）两个标记（由写入管道负责，不由人肉维护）；②提供**一键清理脚本**，**默认仅清除指定 env 下的 synthetic 记录**，未显式指定 env 时拒绝执行；③清理后**重算全部聚合视图**（含 role_benchmarks 与各看板），防止用合成数据算出的基准残留；④写审计留痕（`audit_logs.event_type = 数据清理`，含清除条数、env、操作者）；⑤清理全过程要求先备份（复用部署文档回滚机制）、停写后再执行。
- **边界**：清除范围不得触及 `env=prod` 或 `data_origin=real` 的记录；**清理测试数据不等于可以接入真实数据**——真实简历需另行补齐告知-同意、留存与删除权、权限体系（PRD §6.3/§10 已声明本期不实现），故"清空"定位为**演示/作品交付前动作**。
- 验收：Given 库中含 synthetic 与 real 混合数据，When 以 `env=demo` 执行清理，Then 仅 synthetic 记录被清除、real 记录完好、audit_logs 生成"数据清理"记录、role_benchmarks 重算后不含清理前的合成统计；Given 未指定 env 或指定 `env=prod`，When 执行清理，Then 拒绝执行并提示必须显式指定非生产环境。

### 6.5 Audit Agent 审计（AU-001~003，横切，P1 随 MVP 简化版落地）

> **本节服务于核心功能的"两面性"**：项目对外承诺"**两端都被审计**"——AU-001 保证敏感属性在**两侧**都不参与判断，AU-002 保证结果不因敏感属性而系统性偏移，AU-003 保证"两侧共用同一把尺"这件事**不随时间悄然失效**（模型/prompt/量规任一变更都可能破坏同尺性）。**没有 AU 层，"双端同尺"就只是实现层的巧合，而不是可验证的承诺。**

**AU-001 敏感属性隔离检查** P0：系统应当保证性别/年龄/民族/婚育等字段在 Matching/Evaluation Agent 的输入与 prompt 中不可见；Audit 每批次抽检可见性配置。
**AU-002 对照简历对偏见检测** P1：系统应当支持上传仅修改敏感属性的对照简历对，输出**档位差异**（逐维比较）；**任一维度档位差 ≥1 档**即产生审计告警记录。MVP 可用离线脚本执行，结果人工录入。

**AU-003 定级漂移监控（Calibration Drift Monitor）** P1（v1.5 新增）
- **定位**：面向"AI 系统交付后运维"的能力——模型升级、prompt 修改、量规调整后，**档位判定**可能悄然漂移；系统须能自己发现。
- 系统应当定期（或手动触发）对**锚定样本集**（默认取标注集中 20 对，含各档位样本）重跑定级，计算各维度**跨档率**（该维度上落档发生变化的样本占比）与重复一致性，**单维跨档率 >20%** 即写 `audit_logs(result=告警)` 并提示"建议重校准"（联动 EV-007）；告警同时记录当前 rubric/维度优先级/model/prompt 版本，便于定位是哪次变更导致。
- **错误兜底**：监控任务失败不影响在线定级；样本不足（<10 对）时跳过并记录原因。
- 验收：Given 手工修改一处量规档位描述并重跑监控，When 跨档率超阈值，Then 产生告警记录且可定位到该版本变更；Given 未做任何变更，When 重跑监控，Then 无告警且锚定样本跨档率 ≤10%。

### 6.6 数据看板（DB-001~002，P2）

> **本节服务于核心功能的"可观测性"**：看板衡量的是**核心功能运行得健不健康**（档位分布是否合理、人工改档率是否升高、无法判断率是否异常），**不是"匹配得多准"**——撮合质量没有 ground truth，能观测的只有机制指标（对应 §1.3 核心指标的设计逻辑）。

**DB-001 能力定级看板**：批次**档位分布**、人工改档率趋势、各维度档位分布、证据不足率。
**DB-002 审计看板**：偏见检测结果、敏感属性访问日志、Agent 调用成本统计。

### 6.7 求职者端模块（TM-001~005，v2.1 整节改造）

> **本节服务于核心功能的"求职者侧输入"**：PM 层匹配的一端是求职者。TM 层提供两样东西——①**偏好填报入口**（PM-002 的挂载点）；②**对等的标准视图**（求职者看到的量规、档位、差距说明与企业侧完全同源）。**若求职者侧只有"我给岗位打多少分"而看不到自己被如何衡量，"双选"就退化为单向筛选。**
> 定位：本模块是**同一套能力的反向调用**——企业侧问"这个人适不适合岗位"，求职者侧问"这份岗位要什么、我缺什么"。两侧**共用同一套标准包与量规**（SYS-004），保证口径一致（"两侧用同一把尺"，详见 docs/recruit/10）。
> 数据来源约束：仅**用户自主导入的 JD**（粘贴）与**合成岗位库**；不抓取招聘平台、不代投递、不代管账号。
> **v2.1 改造要点**：①TM-001 新增"**岗位要求体检**"组成（RQ-003 的求职者投影）；②TM-003 由"提升建议清单"**重构为"证据缺口与量规差距说明"**（引用量规原文，不给学习建议）；③TM-004 由"合成岗位库匹配"**替换为"自选岗位集对照排序"**（原形不可用：合成库无真实公司，"值得投的方向"为空）；④TM-005 披露对象扩为"求职者 + 内部诊断"双用。

**TM-001 目标岗位对照（含岗位要求体检）** P0（M1 后段启用）

- 求职者导入**自己的简历** + **一份目标岗位 JD 文本**（粘贴）→ 系统复用 JD-001 解析为岗位画像 → 与本人能力画像（EV-011 定级结果）逐维比对 → 输出：
  - **对照档位（B1~B5 / 档位区间）**、命中清单、缺口清单（**各附简历或 JD 原文引用**）、差距级别（如"要求 L3，证据 L2，差 1 级"）；
  - **岗位要求体检**（RQ-003 的求职者投影）：该 JD 是否存在内部矛盾 / 超同级基准 / 不可评要求，**只陈述事实 + 定位原文**。
- **（v2.3）档位在求职者端的呈现纪律**：本模块是**全系统唯一可以说"档位"字样的对外页面**。理由：求职者用档位看**距离**（我离这个岗位还差多少），这是**对自身有利的信息**；而企业端用档位容易变成**门槛**（我不看 B2 以下的人），这是**对他人不利的工具**。**同一个数字，放在谁手里、指向谁，决定了它是帮助还是伤害。** 因此：**求职者端保留档位 + 强制绑定具体岗位要求；企业端一律改说"与岗位要求的差距"**（详见 §6.3 第 7 条、§6.8）。
- **硬约束**：①表述纪律全部适用（禁"具备/掌握/精通"等能力断言，统一"简历显示/简历描述/简历自评"）；②**不出现录用概率、通过率、薪资预测、竞争力排名**；③首屏/档位表**不得出现"未核验/待核验/真实性"类标签**；④简历数据与目标 JD 数据**严格隔离**，无任何接口可把求职者数据回传企业侧；⑤页面固定显示"分析结果仅供参考，不构成就业建议"；⑥**（v2.3）档位必须始终与某一个具体岗位要求成对出现**——**不得出现脱离岗位的"你的技术等级是 B3"式绝对定级**。求职者端的档位语义是"**距离**"（离这个岗位的要求有多远），不是"**身价**"（我值几斤几两）。**任何一页上，档位旁边必须能看见它在跟什么比。**
- **错误兜底**：JD 非岗位文本 → 提示并允许手工录入画像（复用 JD-001 路径）；简历未完成定级 → 先提示完成能力画像。
- 验收：Given 一份含"精通分布式"要求的 JD 与本人 L2 证据，When 对照，Then 输出该维 **B3** 且标注"差 1 级"，并同时在体检区标注"该要求高于同级基准"；Given 检查任意页面上的档位展示，Then **每处档位均与某个具体岗位要求成对出现**（不存在无参照物的裸档位）；Given JD 无诊断问题，Then 体检区显示"未发现可确定的问题"；Given 输入非 JD 文本，When 提交，Then 返回明确报错并给出手工录入入口，不生成任何适配结论。

**TM-002 岗位适配结构视图** P1（阶段 2）
- 对多个目标岗位聚合输出：**强适配方向**（≥B4）/ **弱适配方向**（≤B3 且证据充分）/ **需补证据区**（L0 项）；复用 EV-009 的三区块规则（docs/07 §E.1）。**无证据项不得与弱适配混淆**。
- 验收：Given 3 个目标岗位的适配结果，When 生成结构视图，Then 三区块正确填充且无证据项不与弱适配混淆。

**TM-003 证据缺口与量规差距说明** P1（阶段 2，v2.1 内容重构）

> **这是 v2.1 中最需要把话说清楚的一处改动**：原形态是"提升建议清单"（"建议系统学习 Kafka，推荐课程…"），**属职业规划判断，无依据、不可验证**。

| | ❌ 原形态（学习/提升路径） | ✅ 重构形态（量规差距说明） |
|---|---|---|
| 输出 | "建议系统学习 Kafka、分布式消息中间件，推荐课程…" | "该维度要求 **L3**（能独立设计并排障）；简历证据为 **L2**（能使用）。**量规差异 → 缺的是「排障 / 设计类经历」这类证据。**" |
| 依据 | 无（属职业规划判断） | **已冻结量规（可引用版本号）** |
| 可验证性 | ❌ 无法验证 | ✅ 完全可验证、可复现 |

- **做法**：读取目标维度要求等级 R 与本人证据等级 L，**引用量规中 R 档与 L 档的行为锚点原文**，输出两者的**定义差异**（即"缺哪类证据"）。
- **硬边界（红线）**：❌ 不推荐课程、书籍、技术路线、学习顺序；❌ 不生成任何可直接粘贴进简历的文案；❌ 不做"你应该转行/应该学别的方向"类判断；✅ **只回答"该档标准是什么、你现在缺哪类证据"**。
- 与 EV-010/EV-008 的关系：企业侧的"待验证清单/追问清单"问的是"**这条要问什么**"；TM-003 回答的是"**这条要补什么事实**"——**同一份分析结果的两个方向投影**，共用同一份缺口数据。
- 验收：Given D4 要求 L3、证据 L2，When 生成说明，Then 输出引用量规 L3/L2 锚点原文的差异陈述，且**不包含任何课程/资源/文案内容**；Given 全部维度达标，Then 返回"当前未发现证据层面的缺口"（不硬造）。

**TM-004 自选岗位集对照排序** P1（阶段 2，v2.1 替换原"合成岗位库匹配"）

- **做法**：求职者粘贴 **N 份 JD**（建议 3–20 份）→ 系统对每份执行 TM-001 → 用 **EV-005 同一套档位排序键**排序 → 输出排序结果与**每一名的依据**。
- **为什么这不叫"推荐"**：①"推荐"暗示系统掌握外部岗位库与推荐算法；本功能**只在用户提供的集合内排序**，不扩展、不补全、不猜；②排序依据与候选人排序**完全同源**（同一把尺）——这正是"两侧用同一把尺"最直观的演示。
- **硬约束**：①**不扩展到用户未提供的岗位**；②**不显示录用概率 / 通过率 / 竞争难度**；③界面命名使用"**岗位对照排序**"，**不使用"推荐""匹配度排名"**等暗示外部数据源的措辞；④每份岗位的来源（用户粘贴）与时间留痕。
- 验收：Given 用户粘贴 5 份 JD，When 排序，Then 输出 5 项按档位排序键的降序结果，每项附"该位次依据"（达标维度数 / 优先级逐维档位比较过程），且**不出现任何概率或通过率字段**；Given 用户粘贴 1 份，Then 提示"至少 2 份才能排序"并回退到 TM-001。

**TM-005 岗位参考基准（Role Benchmark）** P1（阶段 2，v1.8 新增，v2.1 用途扩展）

- **定位**：向求职者展示目标岗位的**常见要求与聚合区间**，作为其能力画像的对照系。**它描述事实，不预测结果**——因此与"录用概率"是两类东西（前者可验证、可对照；后者不可验证、易误导）。
- **命名纪律（v2.3 依红线 14）**：本模块**不使用"达标线"字样**（"线"字隐含门槛语义），一律表述为"**该岗位常见要求**"；**全模块零阈值语义**（禁"合格线/达标线/分数线/淘汰线"）。
- **数据来源（三档，须在界面标注）**：
  - **A 档｜推导基准**：由岗位画像的要求等级 R 直接推导该岗位的常见要求（如"Go L3、MySQL L2、1 个可验证项目"）——**不涉及任何历史数据**；
  - **B 档｜合成样本统计**：基于合成岗位库的合成达标样本集生成分布（如"常见缺口 Top3"），**必须标注"合成样例统计，非真实录用数据"**；
  - **C 档｜真实录用回流**：**阶段 3 且须企业书面授权**；仅此档可称"录用"字样。
- **v2.1 用途扩展（双消费者）**：TM-005 同时作为 **RQ-003 判定"超出同级岗位基准"的依据**——**同一份基准、两个消费者**（生产侧为 SC-002，见 §6.9）。
- **五条披露硬约束（不可砍）**：①**聚合优先**——只展示分布/区间/常见要求，永不展示个体画像；②**k-匿名门槛**——任一维度或组合样本数 <20 时显示"样本不足，暂不展示"，不得输出任何统计（**服务层强制**，非界面层）；③**不回传竞争信息**——不展示排名、"击败 X%"、"某人比你强/弱"；④**敏感属性零出现**（沿用 AU-001）；⑤**双侧数据隔离**——求职者为只读聚合视图，无任何接口可返回个体记录。
- **"我的位置"表述规则**：只与**该岗位常见要求/区间**比较（如"你的 Kafka 为 L0，低于该岗位常见要求 L2，差 2 级"），**禁止与任何个体或人群排名比较**。
- **边界**：不出现"录用率/录用人数"（A/B 档下无真实数据）；不设任何筛选门槛与阈值语义；不构成就业建议。
- 验收：Given 基准样本数 12（<20），When 查看基准，Then 显示"样本不足，暂不展示"且无任何统计泄露；Given B 档基准，When 展示常见缺口，Then 页面标注来源为"合成样例统计"；Given 任意查询，When 尝试获取个体级记录或排名，Then 无接口可返回；Given 真实录用回流（C 档，阶段 3），When 生成基准，Then 仅写入聚合统计并记录审计日志。

**评测（复用现有标注集，零新增标注成本）**：求职者端对照一致性 ≥90%（与 EV 层同口径）、方向稳定性（重复 3 次波动 ≤1 档）、量规差距说明可用性 ≥70%（人工抽检）、证据可追溯 100%。

### 6.8 双边偏好与匹配模块（PM-001~005，v2.1 新增；**v2.2 确立为产品核心功能，移入 M1**；**v2.3 新增 PM-005 档位措辞分端**）

> **定位**：**本模块是本产品的核心功能**，其余模块（JD/RQ/MT/EV/TM/SC）均为服务于它的支撑件（见 §1.1.1）。**双边各自填写偏好表单 → 系统用同一套偏好维度逐维比对 → 输出四态档位**。
> **为什么它是核心**：企业侧筛选与求职者侧对照各自只能回答"我这一端怎么看"；**只有本模块回答"两端是否对得上"**——而后者才是"双选"这个词的全部内容。
> **三条护栏（缺一则本模块不成立）**：①**不做撮合结论，只做基于双方填报的匹配建议**（建议 ≠ 决策）；②**匹配依据必须来自双方主动填报的字段**，不由系统从自然语言中"感觉"推断；③**匹配输出不得使用百分比与精确分数**，只出档位语义——**企业端统一说"与岗位要求的差距"，"匹配度"一词亦不使用**（v2.3.2 修正；禁用"匹配度 87%"这类退化写法）。
> **v2.3 新增第四条护栏**：④**档位是两端共用的一把尺，但只说给两端听不同的话**——企业端说"与岗位要求的差距"，求职者端说"档位/距离"；**系统有责任阻止档位被企业当作筛选分数线使用**（红线 14）。**标尺的刻度由本系统测定，所以本系统不能把它晾成一把判决尺。**
> **实现纪律**：匹配走**确定性规则引擎**，**不走 LLM 自由判断**——LLM 只用于把用户填写的选项映射到维度取值，比对与档位生成由代码完成（保证可复现）。

**PM-001 双边偏好填报** P0（前置：配置 `preference_dimensions` 版本化）

- 系统应当提供两侧偏好表单，共用**唯一版本化的偏好维度表**（`dimension_version`）。**必填收敛至 3 项**：①**技术方向** ②**自主性** ③**学习与成长倾向**；**选填其余 5 项**：协作密度 / 反馈频率 / 工作节奏 / 成长路径 / 技术挑战度。
- **每项均允许"无法判断/不愿透露"**，记为 `未填报`——**不代填、不猜测**。选填项跳过亦记 `未填报`。
- 企业侧额外可填写**氛围描述**（自由文本），页面固定标注"**本内容由企业自行填写**"，与系统推导结论**分区显示**；系统**不代写、不润色、不评判**。
- **硬约束**：①每题给**选项**而非纯自由文本（降低随意性）；②**不允许把必填项扩为更多项**（新增维度一律选填）；③两侧表字段名与选项集**必须同源**（同一 `dimension_version`）。
- 验收：Given 企业侧与候选人侧均完成必填 3 项填报，When 提交，Then 生成带 `dimension_version` 的填报快照；Given 某方对"自主性"选择"无法判断"，Then 该维记 `未填报` 且不参与匹配计算但显式标注；Given 两侧表单的维度版本不一致（一方为旧版本），Then 拒绝匹配并提示升级。

**PM-002 确定性匹配计算** P0

- 系统应当基于双方填报快照，逐维执行**确定性规则比对**，输出每维的**匹配档位（高/中/低/无法判断）**与整体档位；**必填 3 项全部无法判断时，整体档位为"无法判断"**。
- **判定规则（偏好类为区间判断，非精确刻度）**：
  - 两侧落在**同一档位区间** → **高**；
  - 落在**相邻档位** → **中**；
  - **相隔 1 档以上** → **低**；
  - **任一方 `未填报`** → **无法判断**。
  - **技术方向属事实比对**（企业要 Java/Spring，简历有 Java/Spring → 可引用原文），与偏好类的区间判断**输出形态一致但判定依据不同**，实现时须区分（见 docs/recruit/13 §1.5 说明）。
- **硬约束**：①**不出现百分比、精确分数、"匹配度 87%"**；②**不出现"命中 4/5""一致 2 项"这类清单式计数**（观感僵硬、AI 味重）；③**"无法判断"是合法输出**，不得为好看而强行给档；④每个档位**必须可展开到双方原文**，无依据不得出档位。
- 验收：Given 企业侧"自主性=高自主"、候选人侧"自律、学习积极"（落在同一区间），When 匹配，Then 该维输出 **高** 且可展开两侧原文；Given 一方 `未填报`，Then 该维输出 **无法判断** 而非硬给"中"；Given 同一对快照重复执行 3 次，Then 逐维与整体档位**完全一致**（可复现性 100%）。

**PM-003 匹配结果三层输出** P0

**⚠️ v2.3 关键约束（v2.3.2 修正措辞）：同一套档位，两端不说同一种话。** 本模块的**底层判定完全同源**（同一套偏好维度、同一套区间规则、同一套档位定义），但**对外的呈现措辞按端区分**——企业端一律用"**与岗位要求的差距**"（高于要求 / 相符 / 低于要求 {n} 级），求职者端保留"**档位/距离**"。**差异只在措辞，不在算法。** ⚠️ **v2.3.2**：v2.3 原稿此处写企业端用"匹配度"，与 §6.7 第 7 条"一律以**与岗位要求的差距**表述"矛盾，且"匹配度"带数字联想——**已统一收口为"差距"句式**。

| | **企业端（招聘工作台）** | **求职者端（我的画像）** |
|---|---|---|
| 维度呈现 | "技术方向：**与岗位要求相比，高于要求**" | "技术方向：**要求 L3 / 我的证据 L2，差 1 级**" |
| 交互提示 | "自主性：**低于要求 1 级**——双方填报口径相邻" | "自主性：**B3 档**（与岗位要求相比略欠）" |
| 措辞原则 | **只说"与这个岗位差多少"，不说"你被定了几档"** | **可以说档位，但必须与具体岗位同时出现** |
| 底层数据 | 同一份 `dimension_results` + 同一套档位序数 | 同一份 `dimension_results` + 同一套档位序数 |

| 层 | 内容 | 设计理由 |
|---|---|---|
| **默认显示层** | 企业端：「技术方向：**高于要求**」「自主性：**低于要求 1 级**」；求职者端：「技术方向：**差 1 级**」「自主性：**B3**」——**两端都只用档位语义，均不出现百分比** | 满足"无 AI 味、观感轻"的要求；同时**不让企业端拿到一个可当门槛用的裸档位** |
| **展开层（点击后）** | 「依据：企业填写『…』｜候选人填写『…』」——**双向引用原文** | **这是项目不可让渡的底线**：结论可以模糊，依据不能模糊 |
| **无法判断态** | 「**无法判断**（一方未填报 / 双方口径不同）」 | 诚实性设计：允许说"不知道"，比硬给一个"中"更可信 |

- **输出**：还包括**整体档位**与一段**中性摘要句**（陈述哪些维度一致、哪些维度有差异、哪些未填报）。**不得出现"你们很合适/不合适"类撮合结论**，**不得派生任何决策动作**（不自动排序晋级、不自动淘汰、不代发消息）。
- **硬约束**：①整体档位只取 `高/中/低/无法判断`；②页面固定显示"**本结果为双方填报内容的比对，非撮合结论、非录用判断，是否进一步沟通由双方自行决定**"；③**不显示录用概率、通过率、竞争难度**；④**企业端不得出现"档位/评级"字样，也不得出现 B1~B5 符号，且"匹配度"一词同样不使用**（见 §6.3 第 7 条、红线 14；v2.3.2 补"匹配度"）；⑤**企业端与求职者端的第一屏均须默认展示 AI 偏差提示**（见 §6.3"AI 偏差提示"）。
- 验收：Given 一份匹配结果，When 检查企业端首屏，Then 仅显示"高于要求/相符/低于要求/无法判断"类差距表述与 AI 偏差提示，**不出现任何 `B1~B5` 符号、"档位"字样或"匹配度"字样**；Given 检查求职者端首屏，Then 显示档位且每处档位均与具体岗位要求成对出现；Given 点击某维度，Then 展开双方原文引用且 `ent_quote`/`cand_quote` **均非空**；Given 检查整页，Then 无任何撮合结论措辞与"推荐"字样、无百分比。

**PM-004 填报快照与结果可复现** P1

- 系统应当为每次匹配保存**双方填报快照**（含 `dimension_version`）与**匹配结果**；匹配结果须引用快照 ID，**不引用实时填报**（防填报变更导致历史结果不可复现）。
- 结果记录须包含：`dimension_results`（逐维四态档位 + 双方原文引用）、`overall_tier`、`dimension_version`、`created_at`。**不得包含任何百分比、分数、权重字段**。
- **硬约束**：①**结果不派生决策动作**；②清理合成数据时须校验**孤儿快照引用**（快照被清而结果残留 → 结果失效，见 docs/recruit/03 §11、12 §2.3）。
- 验收：Given 一次匹配完成后任一方修改填报，When 查看历史结果，Then 仍显示当时的档位与当时的原文引用（未被新填报覆盖）；Given 同一快照重复执行匹配，Then 输出 100% 一致；Given 执行合成数据清理，Then 无孤儿 `match_results` 残留。

**PM-005 档位措辞分端渲染** ★P0（v2.3 新增，M1）

- **需求**：系统应当**以同一份 `match_results` 记录为唯一数据源**，在企业端渲染为"**与岗位要求的差距**"（高于要求 / 相符 / 低于要求 {n} 级）、在求职者端渲染为"**档位 / 距离**"（B1~B5 档 + 相差级数）；**两端档位语义必须完全一致**（同一 `match_id`、同一 `rubric_version`、同一序数），**仅措辞不同**。
- **配置**：措辞映射表、AI 偏差提示文案（首屏句 / 页脚句）、阈值词黑名单**集中于 `config/presentation`**（`GET/PUT /config/presentation`），**不散落于页面代码**——保存时即校验（提示文案须含"可能存在偏差 + 不设合格线"两要素；措辞映射不得含 `B1~B5`、"匹配度"与阈值词，命中即拒绝保存）。**该黑名单是唯一词表来源**，一切消费方（UI 自查脚本、渲染校验、导出过滤）只读不另立（v2.3.2）。
- **硬约束**：①**严禁为企业端单独计算一套结果**——必须复用同一份记录，否则红线 13（两侧口径同源）与本条同时失效；②企业端渲染结果**全文无 `B1~B5`、无"档位/评级"字样、无"匹配度"字样、无任何阈值语义**（v2.3.2 补"匹配度"）；③求职者端**不得出现裸档位**（每处档位必须与具体岗位要求同屏）；④两端结果页**首屏与页脚均须默认可见 AI 偏差提示**（不得折叠 / 可关闭 / 需点击）。
- **验收**：Given 同一 `match_id`，When 分别在两端渲染，Then **两端档位语义完全一致**（同一记录、同一序数），**仅措辞不同**；Given 企业端渲染结果，When 全文扫描，Then **无 `B1~B5`、无"档位/评级"、无"匹配度"、无"合格线/达标线/分数线/淘汰线/门槛"、无 `数字+%` 组合**（v2.3.2：自查词表须与 `config/presentation` 的 `banned_terms` **同源**，不得另立）；Given 两端结果页首屏与页脚，Then **均含 AI 偏差提示且默认可见**；Given 渲染层试图为企业端单独计算，Then **拒绝**（须复用同一记录，红线 13/14）。
- **关联红线**：13、14。

### 6.9 标准自检模块（SC-001~002，v2.1 新增，阶段 2，内部）

> **本节服务于核心功能的"尺子本身"**：PM 层输出"匹配档位"的前提是**尺子本身是准的**。若一份明确写"后端开发"的简历在后端岗位画像下都匹配不出对应档位，那么 PM 层输出的所有档位都失去意义。本模块**不对外**——它检查的不是候选人，也不是企业，而是**系统自己的标准**。
> **边界**：**无对外接口、无对外页面**；产出仅进内部自检报告与 RQ-003/TM-005 的数据源。

**SC-001 画像可辨识性自检** P1（内部）

- 系统应当用标注集简历**反向恢复岗位类型**，输出**画像可辨识率**（与标注一致的比例）；可定位到**失配的具体维度**。
- 可辨识率低于目标时**产生待校准提示**（联动 EV-007），**不自动改量规**。
- 验收：Given 标注集 20 份简历，When 执行自检，Then 输出画像可辨识率且可定位到失配的具体维度；Given 可辨识率低于 70%，Then 产生待校准提示（**不自动改量规**）。

**SC-002 同级岗位基准（生产侧）** P1（内部，供 RQ-003 与 TM-005）

- 以合成岗位库为底座推导**同类岗位要求区间**（如"后端校招：Go L2–L3、MySQL L2、1 个可验证项目"），来源标注 `A 档｜推导基准` / `B 档｜合成样例统计`。
- 样本数 <20 时不输出任何统计（k-匿名门槛，**服务层强制**）。
- **TM-005 是它的对外披露投影**（同一份基准、两个消费者）。
- 验收：Given 某岗位类型样本 <20，When 生成基准，Then 不输出任何统计（显示"样本不足"）；Given 基准可用，Then 每条数据标注来源档位，且不含任何个体画像。

### 6.10 红线清单（十四条，v2.3 全文收录）

> **长期有效，不因版本迭代而放松。** 本清单是定位（双边偏好匹配平台）成立的前提；**若某条被突破，定位即失效**。原 §3.2"长期不做（红线）"四句为本清单的子集，已由本节取代。**v2.3 新增第 14 条（档位不得被用作筛选门槛）。**

| # | 红线 | 理由 |
|---|------|------|
| 1 | **不做强制撮合、不做自动决策**：允许基于**双方主动填报字段**输出匹配建议；**建议非强制，判断权归用户**；**不做自动淘汰、不做自动排序晋级** | 撮合质量无 ground truth；"建议"不承担"建议对了"的责任，只承担"依据可追溯"的责任。**用户量属运营职责，不作为系统指标** |
| 2 | **不生成企业介绍、企业文化叙述、雇主品牌内容**：企业**自行填写**的氛围描述可录入并展示，但**系统不代写、不润色、不评判其好坏** | 生成属不可验证的营销内容；"企业自填"与"系统生成"是两类东西 |
| 3 | **不从公开渠道抓取公司信息生成企业画像** | 幻觉风险最高的一类（编造公司情况，企业可追责） |
| 4 | **不代写 JD、不提供"改写后的岗位描述"** | 属代写/包装类；只诊断，不改写 |
| 5 | **不抓取招聘平台岗位数据；亦不通过第三方"聚合 API"间接获取**（例外：24365 等**面向公众的公开浏览接口**匿名可取，不属此列） | 违反平台条款与用户协议；外包不改变性质 |
| 6 | **不承诺面试通过率、录用概率；不做薪资预测**；**匹配结果不得使用百分比与精确分数**，只出档位（高/中/低/无法判断） | 无 ground truth，不可验证；数字造成伪精确预期，无法回答"为什么不是 92%" |
| 7 | **不推荐课程、书籍、学习路径、技术路线** | 属职业规划判断，无依据支撑；只做量规差距说明（TM-003） |
| 8 | **不做个体级录用数据展示与候选人排名**（含"击败 X%"式对比） | 隐私与反向识别风险 |
| 9 | **披露纪律对两侧一致**：聚合优先、k-匿名 ≥20（**服务层强制**）、不回传竞争信息、敏感属性零出现；示例企业与合成岗位必须 `data_origin=synthetic` 显式标注 | TM-005 五条纪律升格为通用红线 |
| 10 | **表述纪律适用于标准侧与求职者侧**：只陈述事实 + 定位原文，不评价企业、不做 JD 好坏总评、不做能力断言 | 与"证据整理者而非认定者"定位一致 |
| 11 | **求职者端不生成任何可直接使用的文案** | 防止蜕变为简历包装 |
| 12 | **匹配结论必须可展开到双方原文**：无依据不得出档位；**允许并鼓励输出"无法判断"** | 这是与市面上任何 AI 匹配工具的分界线——**结论可以模糊，依据不能模糊** |
| 13 | **两侧填报字段口径必须同源**：偏好维度表为**唯一版本化配置**（走 EV-007 版本纪律），两侧不得各用一套维度 | "两侧用同一把尺"是定位成立的必要条件（§1.1） |
| **14** | **档位不得被用作筛选门槛**（v2.3 新增）：①**企业端不出现"档位/评级"字样**，一律以"与岗位要求的差距"表述；②**系统不设任何阈值语义**（禁"合格线/达标线/分数线/淘汰线"）；③**AI 偏差提示须在企业端首屏与页脚默认可见**；④**两端底层判定同源、措辞区分**（企业端=差距，求职者端=档位） | **这是产品伦理的底线**：档位是"辅助判断的参照"，一旦被当作录取门槛，系统即从"帮你看证据"变成"替你下判断"，定位当场失效。**标尺的刻度由系统测定，因此系统有责任阻止它被当成判决书** |

## 8. 业务流程与状态流转

**简历流转状态机**：已导入 → 解析成功/解析失败（转人工）→ 待初筛 → 已分批（高匹配/潜力/存疑 + 未达门槛标记）→ 待定级（仅高匹配/潜力批可选入定级队列）→ 定级完成（待人工确认）→ 已确认 / 已打回（重定级）→ 进入候选人排序输出。

**报告状态机**：待确认 →（HR 操作）已确认 / 部分修正（单维改档）/ 已打回 →（重定级后）待确认。所有状态迁移记录操作者与理由。

**主流程（企业侧）**：JD 导入(JD-001) → 画像确认(JD-002) → 【阶段 2：需求澄清(RQ-001) → 要求溯源(RQ-002) → JD 诊断(RQ-003) → 覆盖校验(RQ-004)】→ 简历导入(MT-001) → 规则过滤(MT-003) → 软匹配分批(MT-002) → 定级队列(EV-001~005) → 报告(EV-006) → 人工闸门(SYS-001) → 校准记忆(SYS-002) → 排序输出。

**主流程（求职者侧，阶段 2）**：简历导入 + 目标 JD 粘贴 → 能力画像（EV-011） → 目标岗位对照(TM-001，含岗位要求体检) → 量规差距说明(TM-003) → 多份 JD 时对照排序(TM-004) → 岗位参考基准(TM-005)。

**主流程（双边匹配，阶段 2）**：企业侧填偏好与氛围(PM-001) → 候选人侧填偏好(PM-001) → 版本一致性校验(dimension_version) → 确定性匹配计算(PM-002) → 三层输出(PM-003) → 快照留存(PM-004) → **双方自行判断，系统不派生任何决策动作**。

**状态机补充（v2.1）**：
- **需求层状态**：JD 已解析 → 待澄清（RQ-001）→ 已澄清/部分未澄清 → 已诊断（RQ-003）→ 已确认 Brief。`未澄清` 项**不阻塞流程**，仅标注并不进入 P0。
- **匹配状态**：待双边填报 → 单边已填 → 双边已填（可匹配）→ 已匹配（快照锁定）。**任一方修改填报不回溯历史结果**（PM-004），仅生成新快照。

### 9.2 评测数据集

| **档位被当作筛选动作的依据**（v2.3） | 试图以档位（或企业端差距表述）配置自动淘汰、自动排序晋级、自动过滤 | **系统层面无此接口**（PM-003/PM-004 不派生决策动作，红线 1/14）；若有外部脚本或导出后处理触发，须在导出文件头显式声明"本文件不含录取建议，档位不可用作筛选门槛" | 无需恢复，属设计内拒止；如为界面误导所致，修正文案 |
| **求职者端出现无参照物的裸档位**（v2.3） | 页面出现"你的技术等级 B3"而未同时展示具体岗位要求 | 提示为展示缺陷：**校验档位与其参照岗位成对**，缺失则回退为"（未选择对照岗位）"占位，不出档位 | 选择对照岗位后重新生成 |

## 13. 风险与遗留问题

| 风险/遗留 | 等级 | 应对/说明 |
|----------|------|----------|
| 标注集主观性 | 中 | 3 人标注+Kappa 门槛；宁可指标朴素勿造假 |
| GPA 维度公平性争议 | 中 | 百分位定档 + **优先级压至最低（P2 参考级）** + README 声明参考信号；院校不加分 |
| **定级结果被当淘汰线** | **中**（v2.3 由"低"上调） | **v2.3 起视为产品伦理风险而非表述风险**：仅靠"系统不输出总分、不设分数线"已不足以保证——**企业完全可能自行把档位解读为门槛**（"B2 以下不看"）。故升级为**结构性约束**：企业端不出现档位字样、改用"与岗位要求的差距"表述；全站零阈值语义；两端首屏与页脚默认展示 AI 偏差提示；系统不提供任何按档位自动过滤/淘汰的接口（红线 14）。**残余风险承认**：无法阻止用户口头转述，故以"降低可操作性 + 明确辅助定位"作为应对，不追求彻底消除 |
| 红海同质化 | 中 | 依赖三支点（Agent 深度/垂直技术岗/可验证评测），缺一即退回——立项后逐月自检 |
| **澄清问题过多导致填写意愿下降**（v2.1 新增） | 中 | 硬上限 7 题、每题给选项、允许跳过；跳过项标注"未澄清"而非阻塞流程 |
| **JD 诊断误报损害信任**（v2.1 新增） | **高** | 只做三类可确定诊断；每条须定位原文；无问题时不硬造；诊断准确率抽检 ≥80% 后才对外 |
| **"超出同级基准"依赖合成岗位库，基准本身可能失真**（v2.1 新增） | 中 | 基准必须标注来源档位（A 推导 / B 合成）；界面显式标注"合成样例统计" |
| **求职者端被误读为"简历包装工具"**（v2.1 新增） | **高** | 三条硬边界：不生成文案（红线 11）、不推荐课程与学习路径（红线 7）、不承诺通过率（红线 6）；界面文案一律为"描述事实"句式 |
| **匹配结果被误当撮合承诺**（v2.1 新增） | **高** | 界面与文案反复强调"依据双方填报生成的比对结果，非撮合、非录用判断"；整体档位只用档位不用百分比；**不做自动决策**（红线 1）；页脚固定说明 |
| **双方填报质量决定匹配上限**（v2.1 新增） | 中 | 必填收敛至 3 项降低门槛；每项给**选项而非自由文本**；"无法判断"合法，避免被迫乱填；**不代填、不猜测** |
| **偏好维度抽象导致"无法判断"占比过高**（v2.1 新增） | 中 | 手工验证阶段（docs/recruit/13 §10.2 第 3 项）专项检验；若必填 3 项中 ≥2 项无法判断，须改为更具体的选项式描述 |
| **企业氛围自述被当成系统背书**（v2.1 新增） | 中 | 页面固定标注"**本内容由企业自行填写**"，与系统推导结论**分区显示**；系统**不代写不润色不评判**（红线 2） |
| **两端排序结论冲突**（v2.1 新增） | 中 | 两端共用同一排序键（EV-005）与同一标准包；H7 假设专项验证；如仍冲突则查标准包版本是否一致 |
| **企业端措辞被读回百分比/打分**（v2.3 新增，v2.3.2 修正措辞） | **高** | ⚠️ **v2.3.2 修正**："匹配度"一词**已从企业端措辞中移除**——落地时企业端统一为"**与岗位要求的差距**"（高于要求 / 相符 / 低于要求 {n} 级）。原 v2.3 曾以"匹配度"作企业端替代词，但该词**天然带数字联想**（"匹配度 87%"），风险未消除，故不再采用。**风险**：文案中一旦出现"匹配度 87%""匹配度 0.72""契合度 X 分"，全部伦理设计即刻作废（红线 6/14）。应对：①**指标/验收断言"企业端全文无数字+%组合"**；②**"匹配度"已列入企业端禁忌词**（与"档位/评级/B1~B5/阈值词"同列），由 `config/presentation.json` 黑名单与其消费方（UI 自查脚本 `scripts/check_presentation.py`）**同源强制**；③文案模板由配置集中管理，不散落在页面代码；④演示脚本与 UI 原型同步自查 |
| **自查词表与实际禁词不同源**（v2.3.2 新增，源自 docs/recruit/15 评审） | **高** | 实测发现：UI 文档的"出稿前自查"grep 关键词**与系统阈值词黑名单是两套独立词表**——v1.6 版自查要查"阈值语义"却**漏收"门槛"二字**，导致 P3 三处"未达门槛"长期通过自查未被发现；同理企业端"匹配度"未被禁。应对：**词表唯一来源 = `config/presentation.json` 的 `banned_terms`**，一切消费方（自查脚本、渲染校验、导出过滤）**只读不另立**；任一侧加词，另一侧自动生效。**核查工具本身的失实，比被核查内容的失实更危险**（它会让人以为已经查过） |

## 14. 评测与验收总线

评测脚本（`evals/run.py`）一键输出：初筛一致率、**定级一致性（档位一致率）**、证据覆盖率、**人工改档率**基线、偏见检测报告，全部结果连同模型/量规/**维度优先级**版本写入 `evals/report.md`，进 README。

**v2.2 三级指标总线（依 §1.3）**：
- **核心指标（4 项，PM 层）**：匹配结果可复现性、匹配档位依据完整率、匹配档位一致性、无法判断率（记基线）——**对外演示与验收的第一顺位**。
- **支撑指标（11 项，按服务对象分组）**：需求溯源覆盖率 / JD 诊断准确率（基线） / 需求澄清完成度（基线）（RQ 服务）、初筛一致率 / baseline 对比优势（MT 服务）、定级一致性 / 证据覆盖率 / 熟练度定级抽样准确率 / 人工改档率（基线）（EV 服务）、求职者端对照一致性（TM 服务）、画像可辨识率（SC 服务）。
- **作品指标（3 项）**：链路可演示性、交付效率 ≤30 分钟、单份成本 ≤¥0.5。

验收以该报告为准，**任何指标不达标以真实数字呈现，不造假不调参粉饰**。
