本文件取代旧 Streamlit 部署说明。同频部署至 81.70.206.10，当前入口为 **http://81.70.206.10:18082**。2026-10-16 按用户要求从临时自签 HTTPS 改为 HTTP，取消了该端口的证书配置与 HTTPS 跳转。切换前已备份数据卷，保留原账号和所有业务资料；18080、18081 其他应用保持运行。HTTP 没有传输加密，浏览器地址栏仍可能标注“不安全”，但不会出现自签证书拦截页。

原服务器无法连接 PyPI 和 ACME 签发服务，但可连接国内构建镜像与 DeepSeek。镜像构建时补齐前端类型检查引用的 config 目录，最终前端资源哈希与本机生产构建一致。后台进程以 UID 10001 运行，数据卷可写。运行时实测 API 约 71 MiB、web 约 10 MiB，容器均 healthy。

本次 HTTP 切换已通过前端 80 项测试、类型检查和生产构建，以及后端登录相关 40 项测试。生产 Cookie 默认仍为 Secure；当前服务器明确设置 SESSION_COOKIE_SECURE=false。HTTP 会话使用独立的 tongpin_session_http / tongpin_admin_session_http Cookie，保留 HttpOnly、SameSite=Strict、CSRF 与 Origin 校验；不会与旧 HTTPS Secure Cookie 冲突。切换后需要重新登录，业务资料不会清空。前端请求编号支持 HTTP 环境，避免投递、消息和 AI 操作因 crypto.randomUUID 不可用而报错。

公网 HTTP 页面、健康检查和未登录资料权限检查已验证。浏览器登录、刷新和退出检查通过独立的合成测试数据库桥接验证，不会向生产注册测试用户或发送真实短信。首次部署时已在服务器以无个人资料的最小消息验证 DeepSeek 返回 HTTP 200；本次未重复付费模型测试。真实短信送达及本人账号操作仍需由用户验收。没有建立默认用户或管理员。

如恢复 HTTPS，配置受浏览器信任的证书，设置 SESSION_COOKIE_SECURE=true 并重新部署，再修改宿主机该站点的 TLS 配置。APP_ENV 保持 prod，不能通过更改环境标记迁移或清空资料。

## 上线前确认

先只读检查 `cat /etc/os-release`、`uname -m`、`free -m`、`swapon --show`、`df -h /`、`docker version`、`docker compose version`、`docker ps` 和 `ss -lntp`。建议 Docker Compose 2.20+，预留约 2 GB 可用内存、5 GB 可用磁盘；这是同频的预算，还需要为现有应用留余量。构建内存不足时先评估现有应用与 swap，再决定在构建机制作镜像，不能直接重启其他服务。

生产默认启用 Secure Cookie；采用 HTTPS 时保持 SESSION_COOKIE_SECURE=true。当前用户明确选择 HTTP，因此服务器 .env 设为 SESSION_COOKIE_SECURE=false，使用独立的 HTTP 会话 Cookie。该设置只控制 Cookie 传输属性，不会关闭身份、CSRF、Origin 或角色隔离检查。

宿主机 Nginx 使用 docker/tongpin-host.conf.example，将 SERVER_IP 替换为实际地址；只安装同频站点文件，不覆盖全局配置或其他应用。其公网端口为 18082，上游 127.0.0.1:18083。代理保留完整 Host（含端口）、传递实际协议，并覆盖客户端自带的转发 IP 链。修改后执行 sudo nginx -t，再 reload。

SSH 只用于维护，API 8000 与内部 web 18083 不需要向公网放行。若现有代理也是容器，须先检查其网络，不能把代理容器的 127.0.0.1 当作宿主机。

## 准备与启动

源码包排除 .env、私钥、本地 data、测试材料、依赖和 Git 数据；尚未授权迁移的数据不随代码上传。服务器使用独立目录，例如 /opt/tongpin；如目录或同名 Compose 项目已经存在，先检查并备份，不能覆盖未知服务或卷。

```sh
cd /opt/tongpin
umask 077
cp .env.server.example .env   # 仅首次创建；更新时保留服务器原 .env
chmod 600 .env
# 在服务器编辑器中配置 DeepSeek 与短信密钥，不把密钥贴进聊天或命令日志。
docker compose -f docker-compose.server.yml config --quiet
sh deploy-server.sh
```

服务端配置说明：APP_ENV 固定 prod，AUTO_SEED 固定 false，LLM_MODE 固定 live，LLM_DEFAULT_MODEL_ID 固定 deepseek，VECTOR_ENABLED 固定 false。DeepSeek key 必填；base URL 和模型名需与已开通账号一致。新环境 AI 调用预算 COST_BUDGET_CNY 默认 50 元，实际用量在应用中累计，不能把它理解为供应商账户的余额。短信的 access key、secret、签名、模板及已使用的 scheme 必须匹配阿里云配置，region 默认 cn-hangzhou。首次注册和找回密码需要真实短信。

WEB_BIND_ADDRESS / WEB_PORT 控制发布地址，模板默认 127.0.0.1:18082。本次服务器 .env 设为 WEB_PORT=18083，宿主机 Nginx 在公网 18082 提供 HTTP，并配置 SESSION_COOKIE_SECURE=false；对应配置模板见 docker/tongpin-host.conf.example。API_CPUS、API_MEMORY、WEB_CPUS、WEB_MEMORY 控制运行预算。RELEASE_TAG 由部署脚本生成 UTC 时间戳并在成功后写入 .release-tag，不能复用同一标签覆盖旧镜像。

脚本先构建再停止旧容器，升级时同时暂停两库写入，并把整个数据卷备份至 backups/时间戳/data.tar.gz，之后启动并等待两个健康检查。首次部署创建空卷，不导入本地账号；本地 demo 与 prod 数据按 env 隔离，若要迁移，必须单独核对账号、关联材料、环境标记和测试认证，不能只改 APP_ENV 或直接复制单个 SQLite 文件。

## 验收和维护

后续操作使用成功版本标签，防止把镜像标签还原为 local：

```sh
export RELEASE_TAG=$(cat .release-tag)
docker compose -f docker-compose.server.yml ps
docker compose -f docker-compose.server.yml exec -T api python -c 'import urllib.request; print(urllib.request.urlopen("http://127.0.0.1:8000/health").read().decode())'
curl --fail http://127.0.0.1:18083/api/health
curl --fail --head http://127.0.0.1:18083/login
docker compose -f docker-compose.server.yml logs --tail=100 api web
docker compose -f docker-compose.server.yml stop
docker compose -f docker-compose.server.yml start
docker compose -f docker-compose.server.yml restart
```

验收需包括：公网所选协议的首页、/login 和前端静态资源正常；/api/health 为 prod/live、AI 已配置；未登录读取私有资料被拒绝；本人完成验证码注册或原账号密码登录，刷新仍保持登录；招聘端、求职端和管理端身份隔离；在本人授权的材料上运行一次 DeepSeek 分析。不要通过无人确认的付费短信批量测试注册。

新服务器没有默认管理员。工作人员本人注册后，由维护者在服务器运行（将示例手机号替换为本人明确指定的实际手机号）：

```sh
docker compose -f docker-compose.server.yml exec api python scripts/manage_accounts.py promote-admin --phone 工作人员手机号
```

也可使用 provision-admin 预置工作人员身份；首次仍需本人短信验证并设置密码。现有虚拟测试企业不能直接当作真实认证企业上线。

代码更新：保留服务器 .env、.release-tag、backups 和数据卷，上传新源码后再次执行 `sh deploy-server.sh`。部署不使用 down -v；down 会停止本项目，但不加 -v 才会保留数据卷。不执行 Docker 全局清理。

应用回滚：从备份目录的 api-image.txt / web-image.txt 找出旧版标签，确保两者属于同一版本，使用 `RELEASE_TAG=旧标签 docker compose -f docker-compose.server.yml up -d --no-build --wait`。回滚后相应更新 .release-tag。若新版本改变数据库结构，应先停止写入并确认数据兼容；恢复数据另行操作，不能自动覆盖当前卷。

备份包含私有简历和认证材料，目录权限保持仅维护者可读。升级前备份由脚本执行；日常备份另需运维安排，定期复制到服务器之外并验证可恢复，避免只在同一磁盘保存。建议保留最近 7 份升级备份；删除前由维护者核对，脚本不会自动删除。排查磁盘使用 `df -h`、`docker system df`，排查内存使用 `free -m`、`docker stats --no-stream`，构建或启动失败先读对应服务日志，勿删除数据卷。

配置参考：[Docker Compose 服务规范](https://docs.docker.com/reference/compose-file/services/)、[生产部署](https://docs.docker.com/compose/how-tos/production/)、[Nginx 反向代理指令](https://nginx.org/en/docs/http/ngx_http_proxy_module.html)。
